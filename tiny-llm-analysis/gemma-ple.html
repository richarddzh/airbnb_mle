Per-Layer Embeddings 解读

    Per-Layer Embeddings（PLE）：Gemma 3n 的端侧内存黑科技

    这是 esp32-ai 项目"把大模型塞进单片机"所依赖的另一半核心思想。 本报告先如实回答"PLE 有没有一篇论文"，再详解它的原理、代码级实现，以及它如何被 esp32-ai 复刻到单片机上。

    0. 先回答你的问题：PLE 有"论文"吗？

    诚实结论：截至目前，并没有一篇专门讲 Per-Layer Embeddings 的独立学术论文。 PLE 是 Google DeepMind 在 Gemma 3n 中引入的一项架构创新，它的权威出处分散在下面几处，而不是一篇单独的 arXiv 论文。

    1. 背景：Gemma 3n 为什么需要 PLE

    Gemma 3n 是 Google 面向手机/平板/笔记本等"日常设备"优化的生成式模型（与下一代 Gemini Nano 共享架构）， 支持文本、图像、音频多模态输入、32K 上下文、140+ 语言。要在移动设备上跑好大模型，最大的敌人还是内存（RAM）。

    Gemma 3n 用一整套技术压缩内存，PLE 是其中最关键的一环：

    • PLE caching（逐层嵌入缓存）——把大量嵌入参数移出 RAM，缓存到快速本地存储，按需取用。
    • MatFormer（套娃 Transformer）——一个大模型里嵌套小模型，可按需只激活核心子模型。
    • Conditional parameter loading（条件参数加载）——纯文本任务时跳过视觉/音频参数不加载。
    • 此外还有 KVC sharing（KV 缓存共享）与激活量化。

    2. 关键数据：有效参数 vs 原始参数

    Gemma 3n 的命名很特别：E2B、E4B 里的 E 表示 Effective（有效）参数， 它比模型实际包含的总参数量小。参数被分为四组：文本、视觉、音频、PLE。

    型号原始参数（Raw）有效参数 / 内存关键手段
    E2B> 5B≈ 1.91B / ~2 GBPLE 缓存 + 参数跳过 + MatFormer 选择性激活
    E4B8B≈ 4B / ~3 GB

    核心主张：虽然原始参数是 5B/8B，但借助 PLE，模型能以"相当于 2B/4B 模型"的内存开销运行， 从而在手机上跑起本该跑不动的大模型。相比 Gemma 3 4B，Gemma 3n 首字响应约快 1.5 倍、质量更好、内存更小。

    3. PLE 到底是什么、怎么工作

    传统 LLM 在网络最底部有一张巨大的 token 嵌入表，每个 token 只在这里查一次， 得到第一层的输入向量；此后各层靠注意力/FFN 不断更新残差流，不再有逐层的专属嵌入。 PLE 的做法不是替换这张底部嵌入表——它保留底部嵌入，然后额外为每一层再准备一份专属的"逐层嵌入"， 在每层计算的末尾叠加注入进残差流。

    官方原文依据：Google 文档 ai.google.dev/gemma/docs/gemma-3n 的 "PLE caching" 一节写道： "PLE parameters … are used during model execution to create data that enhances the performance of each model layer … cached to fast storage, and then added to the model inference process as each layer runs." （即"提升每一层的表现"、"随每层运行加入推理过程"。）而"传统只在底部查一次"是标准 Transformer 常识，用作对照，非 Gemma 原文。

    为什么这样能省内存？因为这些逐层嵌入表加起来参数量巨大（占了原始参数的一大块）， 但它们是查表读取的：每个 token 在某一层只需要表里的一行。于是可以把整张表放到快速本地存储（flash）， 每步只取用当前 token 当前层需要的一行（约 4KB），而不必把整张表塞进 RAM。这就是官方说的 "PLE caching"。

    3.1 主嵌入表 vs PLE：维度与参数量（叠加而非取代）

    很多人会以为 PLE 是"把底部那张大嵌入表换成小的"，其实相反：PLE 是额外叠加的，而且是四组参数里最大的一块。 以逆向工程参考实现的数值（vocab=262144、主隐藏维 2048、ple_dim=256、30 层）算一笔账：

    矩阵维度参数量作用/位置
    主嵌入表（底部查一次）262144 × 2048≈ 0.537Btoken→首层输入，常驻
    PLE 逐层表（单层）262144 × 256≈ 67.1M该层专属，住 flash
    PLE 逐层表（30 层合计）262144 × 256 × 30≈ 2.01B按 token 逐层查一行

    所以"变小了多少"？——并没有变小。PLE 总量（~2.01B）约是主嵌入表（~0.537B）的 3.7 倍， 也正是 E2B "原始参数 > 5B" 的主要来源。省的是运行内存，不是参数量：这 ~2B 参数被挪到 flash， 每步每层只取一行（256 维）。账正好对上——原始 >5B 里减掉 PLE（~2B，移到 flash）+ 视觉/音频（纯文本时跳过）， 常驻 RAM 的有效参数就落到 ≈1.91B（~2GB）。

    4. 代码级实现（逆向工程还原）

    社区逆向工程项目 reverse-engineering-gemma-3n 还原了 PerLayerEmbedder 的实现， 数据非常具体（以某一实现为准）：

    组件数值 / 类型作用
    vocab_size262144Gemma 3n 完整词表
    embedding_dim256每层逐层表示的维度
    num_layers30Transformer 层数（即 30 张逐层表）
    embeddingsnn.ModuleList装 30 张逐层嵌入表的容器
    主隐藏维2048模型主干隐藏状态维度（该实现）
    边界保护torch.clamp(ids,0,262143)查表前把 token id 夹在合法范围

    每一层在末尾通过一个门控（gating）机制把逐层嵌入注入残差流，五个步骤：

    1. 门控计算：F.gelu(per_layer_gate(hidden)) 把当前隐藏状态投影到 256 维。
    2. 选择性激活：与该层专属的逐层嵌入切片做逐元素相乘。
    3. 投影：per_layer_proj() 从 256 维扩回 2048 维。
    4. 归一化：per_layer_norm()。
    5. 残差相加：加回该层主计算路径的输出。

    为什么用"相乘"而不是"相加"？逐元素相乘是一种条件调制（gating）： 门控向量与逐层嵌入互为"开关"，任一方为 0 都能压制另一方。这比简单地加一个"逐 token 偏置"表达力更强—— 它让逐层嵌入的作用取决于当前上下文。

    4.1 设计辨析：分层"静态注入"会不会限制模型能力？

    这是一个很自然的疑问：PLE 查出来的向量 ple_l[token] 只由 token id 决定，是静态的； 可是到了很深的层，残差流里的隐藏状态早已是高度上下文化、综合了整句信息的表示。 在深层还往里塞一份"只认 token 本身"的静态向量，会不会拖累模型、限制它的能力？下面分三点回答。

    ① 内容静态，但"用多少"是上下文决定的。回看注入公式： inject = norm( proj( gelu(gate(hidden)) ⊙ ple_l[token] ) )。 ple_l[token] 确实是静态源，但门控 gate(hidden) 是从当前上下文化的隐藏状态算出来的。 逐元素相乘 ⊙ 让最终注入 = 静态源 × 动态门控——取哪张卡是静态的，但这一层实际用它的哪些维度、用多强由上下文决定， 所以注入信号本身是上下文相关的，并非"硬塞一个死向量"。

    ② 它是"叠加"而非"替代"，因此不会降低能力上限。注意力 + FFN 这条上下文计算主干原封不动， PLE 只是往残差流里额外加一项。极端情况下若这份静态注入有害，门控只要学成 0，就退化回普通 Transformer。

    关键结论：从表达力看，PLE 的最坏情况 = 恒等（被门控关掉）。 所以它只能帮忙或被忽略，不会让模型比没有它更弱。你担心的"静态注入限制能力"， 只有在它替代上下文主干时才会发生——而 PLE 没有替代主干。

    ③ 它换来的是什么。一张底部嵌入表要用同一个向量服务所有层，而深浅层需要的 token 级特征其实不同 （浅层偏表层/构词，深层偏语义）。PLE 相当于给每一层一份专属、按 token 索引的"特征备忘录"： 深层不必再靠残差流费力地把"原始 token 是谁"一路保留下来，从而腾出主干容量去做上下文综合； 而这些静态特征存在 flash 里几乎不占 RAM。本质上是把一部分"token 级记忆"从必须常驻 RAM 的稠密权重， 挪成了可缓存到 flash 的查表——这是一次参数效率的取舍，而不是能力上限的取舍。

    诚实的边界：你说的"静态"局限理论上确实存在——一张查表无法表达"这个 token 在这个具体上下文里意味着什么"， 这部分本就该由注意力/FFN 承担，PLE 只做互补的静态记忆。更重要的是，PLE 没有公开论文，也没有公开的消融实验 单独衡量"有 PLE vs 没 PLE"对能力的影响；Google 只给了定性结论。因此"到底帮多少、有没有隐性代价"目前无法用公开数据量化。

    6. PLE 如何被 esp32-ai 复刻到单片机

    这正是本合集的闭环。esp32-ai 把 Gemma 3n 的 PLE 思想降三个数量级搬到 ESP32-S3 单片机上， 并在代码注释里明确说它复刻的是"Gemma 的 Gemma…TextDecoderLayer，但去掉了 AltUp"。对照如下：

    逐层输入构成上下文投影 + 逐层查表(RMSNorm(proj(x)/√D) + table·√P) / √2

    洞见迁移：Gemma 3n 面对的是"手机 RAM 有限、flash 充裕"，esp32-ai 面对的是"单片机 SRAM 只有 512KB、flash 有 16MB"。 虽然硬件差三个数量级，但内存层级的"形状"相同——快内存小、慢存储大且擅长稀疏随机读。PLE 正是为这种"形状"设计的， 所以能直接迁移。这就是 esp32-ai 的核心洞见。

    7. 局限与要点

    • PLE 不改变"能力上限"：它只是把"占体积但稀疏访问"的嵌入参数挪出快内存，省的是内存， 不是让模型"更聪明"。真正的推理能力仍由稠密主干决定。
    • 省的是 RAM，不是存储：逐层表仍要占用 flash/存储空间，只是不占宝贵的运行时 RAM。
    • 依赖存储随机读性能：每 token 每层都要从 flash 取一行，若存储随机读太慢会成为瓶颈 （esp32-ai 实测 flash 512B 随机读约 20.3µs，占比极小，验证了可行性）。
    • 没有独立论文：想深挖细节，要同时看官方文档、Gemma 3 技术报告与社区逆向工程，而非某一篇论文。

    8. 给初学者的一句话总结

    PLE（Per-Layer Embeddings）的精髓是："把每层专属、体积巨大但每次只查一行的嵌入表，从 RAM 挪到 flash，用时才取。" Gemma 3n 用它让 5B/8B 模型在手机上以 2GB/3GB 内存运行；esp32-ai 用同一招，让 28.9M 模型在只有 512KB SRAM 的 8 美元单片机上跑起来。 它没有独立论文，但它的思想清晰而通用——凡是"快内存小、慢存储大"的设备，都能受益。
