esp32-ai 深度解读

    esp32-ai：在 8 美元单片机上运行 28.9M 参数 LLM

    项目地址：github.com/slvDev/esp32-ai　 这是一个把 2890 万参数的语言模型完整运行在 ESP32-S3（约 8 美元）单片机上的开源项目。 模型完全在芯片上离线运行，以约 9.5 tokens/秒的速度把故事一个词一个词地写到小屏幕上。

    1. 项目要解决的核心问题

    单片机（MCU）最大的限制是"快内存"极少。ESP32-S3 只有 512 KB 内部 SRAM。 按常规做法，整个模型都必须能从 SRAM 访问，这就把模型规模死死限制住了——这也是为什么此前同类芯片上跑的模型只有 26 万参数。

    作者的破局思路：不再把整个模型放进快内存。语言模型的绝大部分参数其实在"嵌入表（embedding table）"里， 模型对它是查表读取而非参与稠密计算。于是可以把这张 2500 万行的大表留在慢速但巨大的 flash 里， 每个 token 只按需取出用到的那几行（约 450 字节），而真正做"思考"的那一小部分参数留在快内存中。

    一句话总结：让"占体积但不常算"的参数住在慢而大的 flash，让"占计算但体积小"的参数住在快而小的 SRAM。 这正是 Google Gemma 3n/4 的 Per-Layer Embeddings（PLE，逐层嵌入）思想，本项目首次把它落到单片机这一量级的内存层级上。

    3. 模型架构：TinyLM 与五种实验臂

    model.py 定义了一个标准的仅解码器（decoder-only）Transformer， 并用一个 arm 字段切换五种不同的"参数花法"，以做严谨的对照实验。它们共享同一个"核心（core）"参数预算， 区别只在于"额外参数"花在哪里。

    实验臂 arm含义
    baseline完全没有查表参数，就是"今天典型的小语言模型"长什么样
    ple ⭐忠实复刻 Gemma-4 的 PLE：逐层输入 = (RMSNorm(proj(embed)) + table) / √2，逐层门控注入残差流
    ple_notable有全部逐层"管路"，但没有查表。用于隔离：收益到底来自查表，还是来自逐层管路本身？
    fatembed和 ple 花同样的查表预算，但用一个宽输入嵌入在底部一次性降维。检验"逐层"是否比"底部一次性"更值
    bigcore把查表预算改花在"更宽的核心"上。作为"薄核心到底损失多少"的参照

    3.2 参数如何分成三层（核心记账思想）

    项目最关键的洞见之一：参数不该按"总量"记账，而该按"访问模式"记账。model.py 的 param_budget() 把参数分成三类，精确对应 ESP32 的三级存储：

    层级访问模式归宿部署配置下的量
    core 核心稠密、随机、每个 token 都算必须常驻 SRAM（真正稀缺的预算）~559 K
    （推导见 3.3-C）
    stream 流式输出头：稠密，但每 token 顺序扫一遍耗带宽而非 SRAM 容量，可放片外~3.1 M
    table 查表稀疏：每 token 只读一行理想的内存映射 flash 对象25 M
    total 合计28.9 M

    为什么 core 故意不含输出头？把输出头（head）算进 core，会让"大词表"看起来贵得离谱—— 而实际上它只是"慢"（要顺序扫一遍），不是"占快内存"。把它单独记为 stream，才让"用大词表换便宜查表"这一整套设计得以成立。

    3.3 从参数量到内存字节：FLASH 查表 & PSRAM 明细

    上面按参数量分了三层，这里把它们换算成真实字节数，看清楚每层如何落进 16MB flash / 8MB PSRAM。 以下全部基于部署固件的开机诊断（V=32768 D=96 L=6 H=4 F=66 P=128）与 esp32_llm.ino 的实际分配代码，4-bit 量化、group-128。

    (A) FLASH：25M 查表，每 token 只读一行

    逐层嵌入表 ple_table 的形状是 [V, L·P]（llm.h 里 bind_q(&ple_table, V, L*P)）：

    项目算式结果
    表参数量V × (L·P) = 32768 × (6×128) = 32768 × 76825,165,824 ≈ 25.2M
    4-bit 存储25,165,824 × 0.5 B≈ 12.0 MB（住 flash）
    每 token 读取deq_row(ple_table, token) 取 L·P = 768 个 int4768 × 0.5 B = 384 B
    + fp16 分组缩放group-128 → 6 组 × 2 B（每组一个 scale）+12 B ≈ 396 B

    "6 行 ≈ 450B" 是怎么来的：一个 token 的整行是 L·P=768 个值，正好是 group-128 下的 6 个分组（对应 6 层，README 说的"6 rows"）；每组 128×4bit(64B) + 1 个 fp16 scale(2B)=66B，6×66 = 396 B。 官方 README 取整说成 "约 450 字节"（含行字节对齐等余量）。budget.py 只算 int4 载荷则为 6×128×0.5 = 384 B。 三者说的是同一件事，量级 ~400 B。

    (C) SRAM：core 核心的 ~559K 从哪来

    core 是唯一必须常驻 SRAM 的一层，也是整个设计的硬约束。它的定义是 「模型全部参数 − 输出头(stream) − 查表(table)」（model.py 的 param_budget()：core = total − stream − table）。 逐项数一遍（部署 ple 臂：D=96, L=6, F=66, P=128）：

    几个要点：

    • core 不含 tok_emb（=stream 输出头，3.1M）和 ple_table（=table，25M）——它们分别顺序扫、按行查，不占宝贵 SRAM。
    • RESULTS 里 baseline=559K、ple=558K、fatembed=559K，都是靠 make_model() 二分搜索 ffn_hidden 对齐到同一个 ~559K 目标，这样对照实验才公平（否则赢家只会是"谁的 FFN 更肥"）。
    • 换算成 SRAM 字节：559K × 0.5 B（4-bit）÷ 1024 ≈ 273 KB，即 RESULTS 原文的 "273KB at 4-bit"——稳稳落进 512KB 内部 SRAM。正是这个 273KB 约束，反过来把模型压到了 d_model=96 这么薄。
    • budget.py 的简化式 442,368 + 1728·F = 556,416 与精确值差 1,952，正好是所有 fp32 归一化向量之和（6×(96+96+96) + 128 + 96）——简化式忽略了这些小 norm。

    3.4 Transformer 代码构成逐块拆解

    模型采用了一套现代 LLM 的标准组件（与 Llama/Gemma 同源），全部在 model.py 中：

    • RMSNorm：weight · x · rsqrt(mean(x²)+eps)，比 LayerNorm 更省、更稳，eps=1e-6
    • RoPE 旋转位置编码：build_rope 预计算 cos/sin，apply_rope 用"前后半分块（split-half）"方式旋转 Q/K
    • Attention 注意力：一个 qkv 线性层同时产出 Q/K/V，因果自注意力用 PyTorch 的 scaled_dot_product_attention(is_causal=True)
    • SwiGLU 前馈：down(silu(gate(x)) · up(x))，比普通 MLP 表达力更强
    • Block 层：x += attn(norm(x)) → x += ffn(norm(x)) →（若启用 PLE）x += ple_norm(ple_proj(gelu(ple_gate(x)) · ple))
    • 权重绑定（weight tying）：输入嵌入 tok_emb 与输出头 head 共享同一张权重矩阵，省下一大块参数

    3.5 PLE（Per-Layer Embeddings）到底做了什么

    这是全项目的技术核心。普通 Transformer 只在底部把 token 嵌入一次；PLE 则为每一层准备一份专属的"逐层输入"， 在每层残差流上做门控注入。逐层输入由两半构成：

    1. 上下文感知的一半：把当前 token 嵌入 x 经一个投影 ple_model_proj 得到 L×ple_dim， 除以 √d_model，再按层切片做 RMSNorm。
    2. 查表的一半：从巨大的 ple_table（vocab × L×ple_dim = 25M 参数）按 token 取一行，乘以 √ple_dim。

    两半相加再除以 √2，得到每层的逐层输入 ple[l]。层内注入用的是逐元素相乘门控 gelu(ple_gate(x)) · ple[l]——这使它成为"条件调制"而非简单偏置：任一因子都能压制另一因子。

    # model.py forward（简化）
ple = ple_model_proj(x) * d_model**-0.5
ple = ple_proj_norm(ple.view(B,T,L,ple_dim))
table = ple_table(idx).view(B,T,L,ple_dim)      # ← 这一行的 25M 参数住在 flash
ple = (ple + table * ple_dim**0.5) * 2**-0.5    # embed_scale=√ple_dim
# 每层：x += ple_norm( ple_proj( gelu(ple_gate(x)) * ple[:,:,l] ) )

    初始化巧思：逐层分支末尾的 RMSNorm 增益被初始化为 0， 让该分支起始时是一个精确的"恒等空操作（no-op）"。这样每个实验臂都从同一个函数出发， 对照实验测的是"学习能力"而非"初始化运气"。

    4. 如何训练这个小 LLM

    4.1 数据准备（data/prepare.py）

    • 数据源：从 HuggingFace 下载 TinyStories 训练集的前 300 MB 切片（约 7500 万 token）。
    • 分词器：用 tokenizers 训练一个 字节级 BPE，默认词表 4096（--vocab 可覆盖，部署用 32768）。 用前 40MB 文本训练合并表即可。
    • 输出：把全部 token 编码为 uint16 数组，按 train/val（验证占 0.5%）切分， 写成 train.bin / val.bin。词表固定，是为了让不同实验臂的交叉熵可比。

    4.2 训练循环（src/train.py）

    训练脚本的精髓是"核心参数预算对齐"：make_model() 用二分搜索自动调 ffn_hidden， 让每个实验臂命中相同的 core 参数量。否则对照实验毫无意义——赢家只会是"谁的 FFN 更肥"。

    训练元参数默认值
    优化器AdamW，betas=(0.9, 0.95)
    学习率 lr / warmup1e-3 / 200 步
    学习率调度线性 warmup + 余弦退火（衰减到峰值的 10%）
    权重衰减 weight_decay0.1（一维参数/norm/查表/嵌入不衰减）
    batch_size / seq_len32 / 512
    训练步数 steps4000（消融）
    梯度裁剪clip_grad_norm = 1.0
    随机批采样用 memmap 随机切窗口，验证集固定种子 1234 保证各臂同批
    计算精度fp32 全程（无 AMP / autocast / 半精度；权重、梯度、AdamW 状态皆 fp32）

    训练用什么精度？train.py 里没有任何混合精度设置——训练自始至终是 fp32。 4-bit 只在训练结束后由 export.py 做训练后量化（PTQ, Post-Training Quantization），训练过程本身从不接触低精度， 也没有做量化感知训练（QAT）。这也是为什么"4-bit 收益完整保留"值得强调（见 5.2）。

    数据集约 7500 万 token 足以把 1M 级核心"过训练"到远超计算最优点——这正是项目关心的场景（用海量数据把小核心榨干）。

    4.3 消融与扫描（experiments/）

    experiments/*.sh 批量跑不同实验臂 × 不同随机种子 × 不同 ple_dim，用来回答三个问题： ① PLE 是否真的赢 baseline？② 收益来自查表还是管路？③ 加宽行 vs 加多行，哪个更有效？

    • PLE 以同样的核心、同样能塞进 SRAM的前提，比 baseline 好 0.098 nats（≈种子噪声的 16 倍）。
    • "逐层注入"比"底部一次性注入"（fatembed）好 0.046 nats——注入的位置很重要。
    • 控制实验 ple_notable（有管路无查表）在小词表下甚至比 baseline 差：证明收益的全部来源是那张 flash 查表， 这正是 ESP32 方案需要的结论。
    • 词表越大，PLE 优势越大：vocab 4096 时优势仅 +0.025，vocab 32768 时 +0.098（4 倍）。

    5.2 4-bit 量化：收益完整保留

    用分组对称 int4 PTQ（group 128，GGUF-Q4 风格；见 export.py 的 GROUP=128）把包括 25M 查表在内的所有大权重量化后， PLE 相对 baseline 的优势 fp32 +0.101 → 4-bit +0.125，保留 124~128%。原因： 带分组缩放的大冗余查表天生比"每个权重都关键"的小稠密模型更抗量化。headline 无需 QAT。

    6.2 量化权重的读取与矩阵向量乘

    权重以分组对称 int4存储：每行按 group 分组，每组一个 fp16 缩放系数，nibble（半字节）存 值+8（0~15）。 关键函数：

    • deq_row()：把某一行 int4 解量化成 fp32（用于嵌入行、查表行）。
    • matvec_q()：y = W·x，边解 nibble 边乘加，按组乘缩放。matvec_q_range() 支持行区间切分， 以便把巨大的输出头拆到两个核上并行。
    • matvec_q8()：int8 激活路径。先把激活量化到 int8，再做 int8×int8→int32 组内点积。 这段 int32 累加正是 ESP32-S3 的 SIMD int8 点积指令的产物，因此设备 SIMD 核与该标量参考在数值上完全一致——只是更快。

    关键：4-bit 是「存储」格式，不是「计算」格式。没有任何 CPU/MCU 能直接做 4-bit 浮点乘法。 int4 只是把权重压小的编码；一旦要参与计算，必须先解回更高精度。反量化公式很简单： w ≈ (nibble − 8) × scalefp16，其中每 128 个连续权重（group=128）共享一个 fp16 缩放系数， scale = max(|w组内|) / 7（对称量化，量化值范围 −7…+7，存成 nibble 即 值+8 → 1…15）。 一维的 norm 向量根本不量化，始终 fp32。

    llm.h 用 #define MATVEC 一键切换两条计算路径，它们共用同一份 int4 权重，只是激活的精度不同：

    对比项matvec_q（默认 / fp32 激活）matvec_q8（int8 激活，设备端用）
    激活精度fp32 原样每 token 动态量化到 int8：x_scale=max(|x|)/127
    权重int4 nibble 边读边解 (code−8)int4 nibble 解成小整数 (code−8)
    组内乘加(code−8)×x[j] 累加为 fp32，再乘 fp16 组缩放(code−8)×xq[j] 累加为 int32，再乘 (fp16 组缩放 × x_scale)
    累加精度fp32int32 → 末尾才转 fp32
    硬件适配任意 CPU，-O3 自动向量化ESP32-S3 的 Xtensa LX7 向量 int8 点积指令

    无论走哪条路，累加始终在更高精度里做（fp32 或 int32），绝不会"纯 4-bit 相乘再累加"。 区别只在于激活是保留 fp32 还是压成 int8：前者精度最高、用于 PC 对齐金标准；后者把乘加换成整数 MAC， 好让 SIMD 一次算多个——这就是"直接以 4-bit 计算"这个直觉的真相：权重永远要临时解量化，只是解到 int8/fp32 后立刻参与高精度累加。 int8 路径的激活量化是动态的——每个 token 现算一次 x_scale，不需要预先用校准数据集标定。

    同一份 C 如何同时适配 ESP32 与普通 CPU？ llm.h 是可移植标量 C，两端编译同一份代码： ① 普通 CPU / PC：编译成标量循环，靠 -O3 自动向量化；用来把全部 32768 个 logit 对齐 PyTorch 金标准（误差仅 1e-5）。 ② ESP32-S3：int8 组点积映射到 LX7 的向量 int8 MAC 指令；每 token 全量扫描的输出头在开机时一次性从 int4 解包成 int8 常驻 PSRAM（见 6.3），省掉每步的 nibble 解包； 并把行区间拆到两核并行。fp16 缩放系数在两端都用软件 half2float 位运算还原——ESP32 没有 fp16 硬件，普通 CPU 也不必有。

    正确性保证：export.py 会生成一份"金标准 logits"（4-bit 模型对固定 prompt 的输出）。 C 移植版在真机之前，先在 PC 上把全部 32768 个 logit 对齐 PyTorch，最大绝对误差仅 0.00001。

    6.3 片上固件（esp32_llm.ino）的平台优化

    • flash 内存映射：用 esp_partition_mmap 把 model 分区映射进地址空间， 25M 查表始终留在 flash，每 token 只随机读几行。
    • 输出头暂存为 int8：开机时把 tied 输出头（1.64MB）一次性从 int4 解包成 int8 放进 PSRAM， 之后每 token 无需再解 nibble，直接 int8×int8→int32 点积。头体积 2.53MB。
    • 双核并行：输出头的行区间拆到两个 LX7 核（head_worker 任务 + 主任务各算一半）。
    • 只算有效词表：分词器实际只学了 25353 项，填充的行永远不会被采样，直接跳过不算不暂存。
    • 喂看门狗：每约 8 个 token delay(0) 一次，避免任务看门狗复位。
    • 采样用贪心 argmax；prompt 为 "Once upon a time"，生成 200 token。

    6.4 4-bit 量化原理：分组对称 int4 PTQ（GGUF-Q4 风格）到底是什么

    5.2 里那句"分组对称 int4 PTQ（group 128，GGUF-Q4 风格）"其实是四个词拼起来的，逐个拆开就一目了然：

    词含义
    PTQ
    （训练后量化）    		Post-Training Quantization：训练用 fp32 跑完，训练结束后再一次性把权重压成 4-bit。不重训、不做量化感知训练（QAT）。见 export.py / quantize.py。
    int4每个权重只用 4 bit → 16 种取值。这里实际取 −7…+7（对称），存成 nibble = 值+8 → 1…15，两个 nibble 打包进 1 字节。
    对称
    （symmetric）    		量化区间关于 0 对称，没有零点偏移（zero-point）。反量化就是一句 w ≈ q×scale，不用减偏移。适合近似以 0 为中心的权重分布，也让 int8 路径的整数点积更省事。
    分组
    （group-wise）    		不是整张矩阵或整行共用一个 scale，而是把每行切成每 G 个连续权重一组（部署 G=128，消融曾用 64），每组一个独立 fp16 缩放。局部定标 → 精度远高于 per-tensor。
    GGUF-Q4
    风格    		沿用 llama.cpp 的 GGUF Q4 块量化思路：块内对称 int4 + 每块一个 fp16 scale、无零点。本项目只是把"块"设成 group=128、并允许最后一组不足 128 的不补零（ragged）打包。

    量化换算（export.py 的 quant_pack，逐组进行）：

    for gi in range(n_groups):
    a, b = gi*group, min((gi+1)*group, cols)
    seg = x[:, a:b]                                  # 本组的一段权重
    sc  = (seg.abs().amax(dim=1, keepdim=True) / 7).clamp_min(1e-8)
    sc  = sc.half().float()                          # 缩放先 round 到 fp16
    qi  = torch.clamp(torch.round(seg / sc), -7, 7)  # 量化成整数 -7..7
    dq[:, a:b] = qi * sc                             # 反量化重建（golden 用）
codes = (q.to(int16) + 8).to(uint8)                  # 存成 nibble 0..15，两两打包

    要点：缩放 scale = max(|本组权重|) / 7（7 = int4 对称的最大幅值），并先 round 到 fp16 再算反量化， 这样 PyTorch 端和 C 端逐位一致，才能用"金标准 logits"证明 C 移植零误差。一维的 norm 向量不量化，保持 fp32（总量极小）。

    为什么 fp16 scale + group=128 能把 28.9M 参数塞进 < 16MB flash？看"有效位宽"（每个权重平均占多少 bit）：

    方案权重码缩放摊到每权重有效位宽28.9M 体积
    per-tensor int4（一个 scale）4 bit≈0~4.0 bit~14.5 MB
    group=128 + fp16 scale（本项目部署）4 bit16/128 = 0.125 bit4.125 bit~14.9 MB ✓
    group=64（消融）4 bit16/64 = 0.25 bit4.25 bit~15.3 MB
    GGUF Q4_0（block=32）4 bit16/32 = 0.5 bit4.5 bit~16.3 MB

    group 越小越精细，但每组的 fp16 scale 开销越大。项目选 128，正好在精度与"整包 < 16MB flash"之间取平衡 （export.py 注释："fp16 scales + ragged packing keep the 28.9M model < 16MB"）。 至于为什么 4-bit 后精度几乎不掉——见 5.2：大而冗余的查表天生比小稠密核心更抗量化，PLE 优势在 4-bit 下反而保留 124~128%。

    6.5 临时解量化的内存开销 & 同一份 C 如何两端通用（附代码）

    临时解量化几乎不占内存。关键在于两条 matvec 路径都是"边读 nibble、边解、边乘加"， 解出来的浮点值只活在寄存器/几个局部变量里（scale / group_acc / acc / g）， 从不把整块权重展开成 fp32 落地到内存。所以额外开销与模型大小无关。

    额外开销来源随权重大小增长？实际大小
    权重解量化 buffer否0 字节（逐权重在寄存器里完成）
    int8 激活 scratch xq[1024]否1 KB（静态复用，比 fp32 激活更小）
    栈上临时标量 acc/g/scale否几十字节
    deq_row 目标（嵌入行/查表行）否写进本就存在的 scratch（x 384B、trow 3KB）
    对照：若整块解回 fp32 常驻是输出头 12.5MB、查表 100MB

    ① fp32-激活路径 matvec_q（默认；边解量化边乘加，不落地任何 fp32 权重。为清晰略去了不足一字节的 ragged 边界处理）：

    static inline void matvec_q_range(const QT *t, const float *x, float *y,
                                  int row_begin, int row_end) {
  for (int r = row_begin; r < row_end; r++) {
    const uint8_t  *row = t->codes  + (size_t)r * t->row_bytes;
    const uint16_t *sc  = t->scales + (size_t)r * t->n_groups;
    float acc = 0.f;
    for (int gi = 0; gi < t->n_groups; gi++) {          // 逐组
      int begin = gi * t->group, end = begin + t->group;
      if (end > t->cols) end = t->cols;
      float scale = half2float(sc[gi]);                  // 软件 fp16→fp32（两端通用）
      float group_acc = 0.f;
      for (int j = begin; j + 1 < end; j += 2) {
        uint8_t byte = row[j >> 1];                       // 一字节含两个 nibble
        group_acc += (float)((byte & 0xF) - 8) * x[j];    // 低 nibble：(code-8)
        group_acc += (float)((byte >> 4)  - 8) * x[j+1];  // 高 nibble
      }
      acc += group_acc * scale;                          // 每组只乘一次缩放
    }
    y[r] = acc;                                          // fp32 结果，无中间缓冲
  }
}

    ② int8-激活路径 matvec_q8（SIMD 友好；激活一次量化成 int8，权重 int4 解成小整数，做 int8×int8→int32 整数点积）：

    // 每 token 动态把激活量化成 int8（唯一的“额外” buffer 是复用的 1KB xq）
static void quantize_act(const float *x, int n, int8_t *xq, float *x_scale) {
  float xmax = 1e-8f;
  for (int j = 0; j < n; j++) { float a = fabsf(x[j]); if (a > xmax) xmax = a; }
  float inv = 127.f / xmax;
  for (int j = 0; j < n; j++) {
    int q = (int)lrintf(x[j] * inv);
    xq[j] = (int8_t)(q > 127 ? 127 : (q < -127 ? -127 : q));
  }
  *x_scale = xmax / 127.f;
}

static void matvec_q8_range(const QT *t, const int8_t *xq, float x_scale,
                            float *y, int row_begin, int row_end) {
  for (int r = row_begin; r < row_end; r++) {
    const uint8_t  *row = t->codes  + (size_t)r * t->row_bytes;
    const uint16_t *sc  = t->scales + (size_t)r * t->n_groups;
    float acc = 0.f;
    for (int gi = 0; gi < t->n_groups; gi++) {
      int begin = gi*t->group, end = begin + t->group;
      if (end > t->cols) end = t->cols;
      int32_t g = 0;                                     // ← 整数累加器
      for (int j = begin; j < end; j++) {
        uint8_t byte = row[j >> 1];
        int code = (j & 1) ? (byte >> 4) : (byte & 0xF);
        g += (code - 8) * (int)xq[j];                    // int4 × int8 → int32
      }
      acc += (float)g * half2float(sc[gi]);              // 乘组缩放
    }
    y[r] = acc * x_scale;                                // 末尾再乘激活缩放
  }
}

static void matvec_q8(const QT *t, const float *x, float *y) {
  static int8_t xq[1024];       // 全模型最大输入维 128，1KB 足够，且复用
  float xs;
  quantize_act(x, t->cols, xq, &xs);
  matvec_q8_range(t, xq, xs, y, 0, t->rows);
}

    8. 给初学者的总结

    • 它是什么：一个 28.9M 参数、只会写 TinyStories 风格小故事的模型，完整跑在 8 美元单片机上，约 9.5 tok/s。
    • 为什么能塞进去：把 25M 参数的嵌入查表留在 flash（每 token 只读约 450 字节），只让 559K 的核心占用宝贵的 SRAM。
    • 关键思想：Google Gemma 的 Per-Layer Embeddings + "按访问模式而非总量给参数记账"。
    • 可信度：两个随机种子、4-bit 量化后收益仍在、C 与 PyTorch 对齐到 1e-5、真机带宽实测——层层验证。
    • 它不是什么："28.9M 参数"指的是"通过内存层级拆分而常驻的存储参数量"，不代表能力翻倍；它仍是个玩具领域模型。
