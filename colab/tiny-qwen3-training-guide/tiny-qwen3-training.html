    核心设计： 用规模受控的儿童故事语料降低语言建模难度，同时采用现代 Qwen3 decoder 架构。它不是官方 Qwen3 权重的压缩版，而是借用 Qwen3 架构定义训练出的独立小模型。

    2. 数据集：流式读取 TinyStories

    2.1 数据来源与 split

    脚本使用 Hugging Face 数据集 roneneldan/TinyStories ， 分别加载 train 和 validation split。 两者都设置 streaming=True，因此不会先把完整数据集下载到本地磁盘。 

    DATASET_NAME = "roneneldan/TinyStories"

train_dataset = load_dataset(
    DATASET_NAME,
    split="train",
    streaming=True,
)

validation_dataset = load_dataset(
    DATASET_NAME,
    split="validation",
    streaming=True,
)

    流式模式把数据集表现为 iterable：训练器按需从远端或缓存中连续取样。 这很适合 Colab，因为它减少磁盘占用和启动等待，但也带来两个影响：

    • 无法像 map-style dataset 那样随机索引或直接获取精确长度。
    • 数据读取和逐条 tokenization 可能成为训练吞吐的瓶颈。

    2.2 数据规模、token 总量与样本

    Hugging Face datasets-server 给出的官方 split 统计如下。样本数是数据集本身的 固定属性；token 数则依赖 tokenizer，因此下表的 token 统计是使用本项目发布的 richarddzh/tiny-qwen3-30m 8K tokenizer 对全量数据逐篇实测得到的， 不是 GPT-2 tokenizer 或论文中的估算值。官方元数据中的解压后 dataset size 为 2,025,789,179 bytes，约 1.89 GiB。

    “追加 EOS 后 tokens”与 notebook 的真实训练流一致： 每篇故事先执行 strip()，然后 add_special_tokens=False 编码，最后追加恰好 1 个 <|endoftext|>。训练集约 4.668 亿个可 packing token， 可切出 911,743 条完整的 512-token 序列，最后余下 203 token 不会形成训练样本。

    2.3 有限缓冲区打乱

    训练 split 使用固定随机种子 42 和大小为 10,000 的 shuffle buffer： 

    train_dataset = train_dataset.shuffle(
    seed=42,
    buffer_size=10_000,
)

    对流式数据而言，这不是全局随机排列。系统先填充一个 10,000 条样本的缓冲区， 每次随机取出一条，再用后续样本补位。buffer 越大，样本顺序越接近全局 shuffle， 但内存占用也越高。固定 seed 让同一数据流的打乱过程具有可复现性。

    3. Tokenizer：从 10 万篇故事训练 8K BPE

    3.1 为什么不直接使用 Qwen tokenizer

    大模型 tokenizer 往往有数万到十几万 token。对于只有约 30M 参数的模型， 过大的词表会让 embedding 和输出层消耗过多参数。脚本把词表限制在 8,192， 使参数预算更多地留给 Transformer 层。

    3.2 训练语料与批量迭代器

    项目配置含义
    Tokenizer 训练样本100,000 篇从训练流前部读取非空故事
    迭代 batch1,000 篇减少 Python 调用和 tokenizer trainer 开销
    目标词表8,192含普通 token 与 special tokens
    最低词频2低于该频率的合并不会进入 BPE 词表
    最大长度1,024写入 fast tokenizer 配置

    3.3 分词管线

    底层使用 Hugging Face tokenizers 库，管线由四部分组成：

    1. NFC Unicode normalization：统一等价 Unicode 表示。
    2. ByteLevel pre-tokenizer：先映射到字节层面，避免大量 OOV 字符。
    3. BPE model：反复合并高频相邻符号，形成子词。
    4. ByteLevel decoder：把 token 序列无损还原为文本。
    raw_tokenizer = Tokenizer(models.BPE(unk_token="<unk>"))
raw_tokenizer.normalizer = normalizers.NFC()
raw_tokenizer.pre_tokenizer = pre_tokenizers.ByteLevel(
    add_prefix_space=False
)
raw_tokenizer.decoder = decoders.ByteLevel()

    Token用途脚本中的角色

    <unk>未知 tokenBPE 模型的 fallback token
    <|im_start|>BOS保留聊天模板风格的起始标记，但训练 packing 未主动插入
    <|im_end|>额外 special token预留消息结束标记，当前训练数据未主动插入

    已保存输出： notebook 确认词表大小为 8,192，EOS token ID 为 0。 示例 Once upon a time, there was a little robot. 被编码为 11 个 token，并可正确解码回原文本。

    4. 模型架构：29.568M 参数的 Qwen3

    4.1 配置总览

    参数值说明

    num_attention_heads8Query heads

    rms_norm_eps1e-6RMSNorm 数值稳定项

    4.2 intermediate size 与 hidden size 的关系

    hidden_size=512 是每个 token 在残差流中的主表示宽度； attention 和 MLP 的输入、输出最终都回到 512 维。 intermediate_size=1408 则只存在于每层 MLP 内部： token 表示先从 512 维扩展到 1,408 维，进行门控非线性变换，再压回 512 维。

    intermediate_size / hidden_size = 1408 / 512 = 2.75

    普通 Transformer 的 GELU FFN 常用 4 × hidden_size， 但它只有 up 和 down 两个大矩阵。SwiGLU 多了 gate 矩阵，共有三个大矩阵。 为了在增加门控能力的同时控制参数量，常取 intermediate_size ≈ (8/3) × hidden_size： 对 512 维约为 1,365，再向适合实现的 64 倍数取整为 1,408。 这里的 1,408 是配置时主动选择的架构超参数，并非框架自动计算。

    4.3 1,024 上下文上限从哪里来

    这个数字直接来自 notebook 中的 MODEL_MAX_LENGTH = 1024，并同时写入 Qwen3Config.max_position_embeddings 和 tokenizer 的 model_max_length。它是作者在能力、显存和计算成本之间做出的设计选择， 不是根据最长故事、词表大小或 hidden size 自动推导出来的。

    Qwen3 使用 RoPE，而不是长度为 1,024 的可学习位置 embedding 表。 max_position_embeddings 仍用于声明模型支持范围、生成长度检查和缓存管理； rope_theta=1,000,000 决定旋转位置编码的频率尺度，但不会自动把可靠 上下文长度变成无限。未经专门扩展和训练，不应把超过 1,024 的输入视为受支持行为。

    4.4 GQA 如何降低参数与缓存

    Query 使用 8 个 head，而 Key/Value 只使用 2 个 head。这是 Grouped Query Attention（GQA）：多个 query heads 共享较少的 K/V heads。 因此 Q 投影输出宽度为 512，而 K、V 投影输出宽度各为 2 × 64 = 128。

    Q projection: 512 × 512 K projection: 512 × 128 V projection: 512 × 128 O projection: 512 × 512

    与 8 个 K/V heads 的标准多头注意力相比，GQA 减少了 K/V 投影参数， 并在生成阶段降低 KV cache 占用。

    4.5 精确参数量拆解

    模块计算参数量
    Token embedding / tied LM head 8192 × 512 4,194,304
    每层 Attention 投影 Q + K + V + O 655,360
    每层 SwiGLU MLP gate + up + down 2,162,688
    每层 RMSNorm 输入、attention 后、Q norm、K norm 1,152
    9 个 decoder layers 9 × 2,819,200 25,372,800
    最终 RMSNorm 512 512
    总计 embedding + 9 layers + final norm 29,567,616

    4.6 SwiGLU 三个矩阵的形状

    PyTorch Linear(in_features, out_features, bias=False) 的权重存储形状是 [out_features, in_features]。因此每层 Qwen3 MLP 的三个无 bias 矩阵为：

    矩阵权重形状参数量作用
    gate_proj [1408, 512] 720,896 把 512 维输入映射到 1,408 维，并经 SiLU 形成门控值
    up_proj [1408, 512] 720,896 把同一输入映射为被门控的 1,408 维内容
    down_proj [512, 1408] 720,896 把门控后的中间表示压回 512 维残差流
    合计 三个矩阵，均无 bias 2,162,688 down(SiLU(gate(x)) × up(x))

    4.7 为什么 RMSNorm 也有参数

    RMSNorm 先按最后一个维度计算均方根，把向量归一化，再乘一个可训练的缩放向量 γ：

    RMSNorm(x) = x / sqrt(mean(x²) + eps) × γ

    归一化操作本身没有参数，eps=1e-6 也是固定常量； 参数来自每个特征维度各一个可学习 gain γ。它让模型在获得数值稳定性的同时， 仍能学习每个通道应保留或放大的尺度。RMSNorm 通常没有 LayerNorm 的可学习 bias。

    每层 Normγ 的长度参数量
    输入 RMSNorm512512
    Attention 后 RMSNorm512512
    Q head RMSNorm6464
    K head RMSNorm6464
    每层合计—1,152

    Q/K norm 的 64 维 gain 作用在每个 attention head 的最后一维， 同一组 64 个参数会广播应用到所有对应 heads；它不是 8 × 64 或 2 × 64 套独立参数。 此外，9 层之外模型末尾还有一个独立的 512 参数 RMSNorm。

    为什么 tying 很重要： 如果输入 embedding 与输出 LM head 不共享，输出层还要增加 8192 × 512 = 4,194,304 个参数，总量会超过 notebook 设置的 30M 上限。脚本用底层 data pointer 断言确认两者确实共享。

    5. 训练样本构造：连续 token packing

    5.1 为什么训练长度使用 512

    模型配置支持 1,024 token，但训练数据固定为 512 token。代码注释明确指出： 先使用 512 以提高 Colab T4 上的训练速度。注意力计算量随序列长度近似二次增长， 因此从 1024 降到 512，attention score 矩阵的理论规模约降为四分之一。

    推理时 prompt tokens + generated tokens 超过 512 并不会立刻发生形状错误， 只要总长度不超过配置的 1,024，模型和 RoPE 仍可计算。例如 700-token prompt 生成 200 tokens，总长度 900，在架构层面是允许的。

    但质量没有同等保证： 训练只见过位置 0–511，位置 512–1023 属于训练分布之外。 模型可能仍能生成，但长程一致性和准确性可能下降。总长度超过 1,024 则超出本模型声明的支持范围，可能被生成长度检查拒绝、出现索引或缓存问题， 或得到不可靠结果。部署 UI 因此应限制 input_length + max_new_tokens ≤ 1024，并把 512 视为质量更可信的范围。

    5.2 Packing 算法

    PackedTinyStoriesDataset 是一个 IterableDataset。 它不把每篇故事单独 padding 到 512，而是把多篇故事连续拼到一个 token buffer：

    1. 读取故事并去掉首尾空白。
    2. 不添加默认 special tokens，直接编码正文。
    3. 在每篇故事后追加 EOS，明确标记故事边界。
    4. 只要 buffer 长度达到 512，就从头切出一个完整序列。
    5. 不足 512 的尾部保留，继续与下一篇故事拼接。
    故事 A tokens
    + EOS
    +
    故事 B tokens
    + EOS
    +
    故事 C tokens
    + EOS
    →
    连续 buffer
    →
    每 512 token
    切成训练样本

    这种方式几乎不浪费 padding token，训练 token 利用率很高。 代价是一个 512-token 序列可能横跨多篇故事；EOS 告诉模型前一篇故事已经结束。

    5.3 Labels 与 causal shift

    每个样本返回三个张量：

    • input_ids：长度 512 的 token 序列。
    • attention_mask：全 1，因为序列没有 padding。
    • labels：直接克隆 input_ids。

    这里不需要手工把 labels 左移一位。Qwen3ForCausalLM 内部会完成 causal language modeling shift：位置 t 的 logits 用来预测位置 t+1 的 token。

    6. 训练前完整性检查

    6.1 数据结构断言

    脚本先从 packed dataset 取一个样本，验证：

    • input_ids、labels、attention_mask 均为长度 512。
    • labels 与 input_ids 完全相等。
    • 最大 token ID 小于 tokenizer 词表大小，避免 embedding 越界。
    • 解码前 500 个字符，人工检查 packing 后文本是否合理。

    6.2 初始 loss 与 perplexity

    随机初始化模型使用 batch size 2 做一次无梯度前向。notebook 保存的结果为：

    项目实际输出
    设备CPU
    输入形状(2, 512)
    Logits 形状(2, 512, 8192)
    初始 loss9.0695
    初始 perplexity8,686.60

    输入形状 (2, 512) 中，第一个维度 2 是 batch size：sanity check 的 DataLoader(batch_size=2) 一次取了两条独立的 packed sequences；第二个维度 512 是每条序列的 token 数。 因而 logits 形状 (2, 512, 8192) 分别表示 “2 条序列 × 每条 512 个位置 × 每个位置对 8,192 个词表 token 的预测分数”。 这里的 2 只用于训练前检查，不是正式训练的 micro batch 8。

    如何理解初始 loss： 如果模型对 8,192 个 token 近似均匀猜测，理论交叉熵约为 ln(8192) ≈ 9.01。实测 9.0695 与这个基线非常接近， 符合随机初始化模型的预期，也说明数据、标签和 logits 维度基本正确。

    6.3 Perplexity 的计算与含义

    因果语言模型 loss 是所有有效 next-token 目标的平均负对数似然（交叉熵）。 Perplexity，简称 PPL，定义为该平均 loss 的指数：

    PPL = exp(cross_entropy_loss) = exp(9.0695) ≈ 8,686.60

    直观上，PPL 可以理解成模型在每一步面对的“等效候选分支数”。 PPL 约 8,686 表示随机初始化模型几乎不知道下一个 token 是什么。 与之对应，正确 token 的几何平均概率约为 exp(-9.0695) = 1 / 8686.60 ≈ 0.000115，即约 0.0115%。

    词表有 8,192 个 token；完全均匀随机预测的理论 PPL 正好约为 8,192。 当前 8,686.60 略高于该值，是随机初始化和有限 batch 波动造成的正常现象。 训练后 PPL 越低通常越好，但它强烈依赖 tokenizer 和评估数据， 不能直接拿不同词表、不同数据集的 PPL 横向比较。

    7.2 Batch 与梯度累积

    参数值
    Micro batch size8 sequences
    Gradient accumulation8 次
    有效 batch64 sequences
    每条序列长度512 tokens
    每个 optimizer step32,768 tokens
    effective sequences / step = 8 micro batch × 8 accumulation = 64 tokens / step = 64 × 512 = 32,768 target tokens = 10,000 × 32,768 = 327,680,000

    梯度累积让显存中每次只驻留 8 条序列，但每累计 8 个 micro batches 才更新一次参数，因此优化器看到的有效 batch 是 64 条序列。 若完整运行 10,000 steps，目标训练预算约为 3.277 亿 token。

    7.3 每个 epoch 的训练数据量

    因为 max_steps=10_000，Trainer 实际按 step 停止，而不是按整数 epoch 停止。不过仍可以用一次完整遍历 train split 定义“自然 epoch”：

    项目每个自然 epoch
    原始故事2,119,719 篇
    正文 tokens464,692,900
    故事边界 EOS2,119,719
    进入 packing 的 tokens466,812,619
    完整 512-token sequences911,743
    完整 optimizer steps（64 sequences/step）14,245

    配置的 10,000 steps 对应 327,680,000 tokens，约为一个自然 epoch 的 70.20%。因此若从头运行到目标 step，理论上不会完整消费一遍全部训练流； notebook 记录到 checkpoint-3500 时约处理 114,688,000 tokens， 相当于约 24.57% 个自然 epoch。

    7.4 LLM 通常需要训练多少个 epoch

    LLM 预训练没有“必须训练若干整数 epoch”的统一答案。大规模语言模型通常更关注 总训练 token 数、tokens per parameter 和 validation loss， 而不是像小型分类任务一样固定训练 10 或 100 个 epochs。 数据集越大、越多样，模型可能在不到一个完整 epoch 时就已经消费了足够多的 token； 数据集较小或领域较窄时，则可能重复 1–3 轮甚至更多，但重复过多更容易记忆训练数据。

    checkpoint-3500 114,688,000 约 3.88 约 0.246
    配置目标 step-10000 327,680,000 约 11.08 约 0.702
    完整自然 epoch 466,812,619 约 15.79 1.000

    一个常被引用的粗略 scaling-law 经验是约 20 training tokens / parameter。对 29,567,616 参数模型， 对应约 5.91 亿 tokens，即约 1.27 个本数据集自然 epoch。 但这个经验来自更大、更广泛的通用语料和模型，只能作为量级参考； TinyStories 领域窄、语言重复度较高，最佳停止点仍应由 validation loss 和生成质量决定。

    对当前训练的含义： checkpoint-3500 只有约 3.88 tokens/parameter，通常仍属于训练早期。 10,000 steps 约 11.08 tokens/parameter，也不算明显过量。 如果 validation loss 仍在下降，仅因为它高于 train loss 就停止，通常会过早。

    8. Checkpoint 恢复与当前训练状态

    8.1 自动恢复机制

    9. notebook 中警告与中断的解读

    9.1 “missing lm_head.weight”

    恢复 checkpoint 时出现： There were missing keys ... ['lm_head.weight']。 该模型设置了 tie_word_embeddings=True，LM head 与输入 embedding 指向同一组权重。某些保存格式会只保存共享参数的一份，因此恢复时可能报告 tied key 缺失。

    判断方式： 如果加载后 embed_tokens.weight.data_ptr() 与 lm_head.weight.data_ptr() 仍相同，并且推理结果正常， 这个提示通常不是模型权重真正丢失。但恢复后重新执行 tying 断言会更稳妥。

    9.2 “1050 > 1024” tokenizer 长度警告

    个别故事编码后达到 1,050 token，超过 tokenizer 声明的模型最大长度 1,024。 但当前 dataset 不会把整篇故事直接送入模型，而是先放入 buffer，再切成固定 512-token 序列，所以真正的模型输入仍然不会超过 512。

    这条警告来自 tokenizer 对单篇文本长度的检查，属于 packing 之前的提示。 若要减少噪声，可以在该编码路径关闭 verbose 警告，或直接调用底层 tokenizer； 不应简单截断每篇故事，否则会改变连续 packing 的 token 流。

    9.3 KeyboardInterrupt 出现在 tokenization 路径

    traceback 停在 self.tokenizer.encode(text)。 这说明逐篇在线 tokenization 可能是训练数据管线的主要 CPU 开销。 GPU 训练时，如果 GPU 经常等待数据，可考虑：

    • 提前把 TinyStories tokenized 并保存为 Arrow、Parquet 或二进制 token 文件。
    • 批量 tokenization，而不是 Python 循环逐篇调用 encode。
    • 在确认不会重复数据的前提下设计多 worker iterable sharding。
    • 把 packing 结果预生成，训练阶段只负责顺序读取定长 token blocks。

    10. Loss 可视化与 TensorBoard

    notebook 通过两种方式观察训练：

    1. TensorBoard： 使用 %tensorboard --logdir "$TENSORBOARD_DIR"， 实时查看 loss、learning rate、eval loss 等 Trainer 日志。
    2. Matplotlib： 从 trainer.state.log_history 提取训练 loss 与 eval loss， 以 optimizer step 为横轴画曲线。

    判断训练是否健康时，建议重点观察：

    • Warmup 前 200 steps 内 loss 是否平稳下降，是否出现尖峰或 NaN。
    • 训练 loss 与验证 loss 是否同步下降。
    • 验证 loss 反弹而训练 loss 继续下降时，是否已经开始过拟合。
    • 恢复 checkpoint 后 learning rate 曲线是否连续，而不是重新 warmup。

    10.1 Validation loss 大于 train loss 是否正常

    正常，而且不能单凭这一点判断应该停止。 Train loss 来自模型正在优化的训练 batches，模型已经直接见过这些数据； validation loss 来自未参与梯度更新的 held-out 数据，本来就通常更高。 此外，Trainer 的 train loss 常是最近若干训练 steps 的区间平均， validation loss 则是在固定 131,072 tokens 上集中计算，两者的采样方式也不同。

    真正重要的是 validation loss 随 step 的趋势，而不是它是否高于 train loss：

    曲线表现判断建议
    Train loss 下降，validation loss 也下降 模型仍在学习且泛化改善 继续训练
    Validation loss 高于 train loss，但持续下降 正常泛化差距 继续训练，不要因绝对大小停止
    Validation loss 单次上升后又下降 可能是评估噪声 观察多个评估点
    Train loss 持续下降，validation loss 连续上升 典型过拟合信号 停止并回退到最低 validation loss checkpoint
    两者长期不再改善 训练进入平台期 停止，或重新调整学习率与数据策略

    10.2 建议的早停规则

    当前每 250 steps 评估一次。不要因为一个评估点变差就停止； 更稳妥的做法是设置 patience 4–8 次评估： validation loss 连续约 1,000–2,000 steps 没有刷新历史最低值，才判定没有继续改善。

    推荐决策： 如果当前只观察到“validation loss 大于 train loss”，但 validation loss 仍总体向下，应继续训练。始终保存 validation loss 最低的 checkpoint， 最终发布最佳 checkpoint，而不是机械地使用最后一个 checkpoint。

    11. 文本补全推理

    11.1 训练模式切换

    训练期间关闭 use_cache，因为 teacher-forcing 会一次计算整段序列， KV cache 不但无益，还可能增加显存占用。生成前则切换为： 

    model.eval()
model.config.use_cache = True

    生成是逐 token 自回归过程，启用 KV cache 可以避免每一步重复计算全部历史 token。

    11.2 生成参数

    参数值效果
    max_new_tokens80最多新增 80 token
    do_sampleTrue使用概率采样，而非 greedy decoding
    temperature0.8降低分布随机性，使文本更稳定
    top_p0.9仅在累计概率 90% 的候选集中采样
    repetition_penalty1.1轻度抑制重复 token
    Random seed42让同一环境下的采样更可复现

    11.3 notebook 保存的生成结果

    Prompt 是： The teacher asked: What is moon? The boy answered: the moon is。 模型继续生成了关于男孩、女孩和月亮的多段文字，其中包括： 

    The teacher asked: What is moon? The boy answered: the moon is very big and dark.

The girl said: "I want to see the moon." The mom said: "Okay, go ahead."

    14. 脚本中值得改进的地方

    14.1 明确保存最终模型

    脚本创建了 FINAL_MODEL_DIR，但没有调用 trainer.save_model(FINAL_MODEL_DIR)。 当前上传逻辑直接读取最新 checkpoint。建议训练完成后显式保存一个最终目录， 让“可恢复训练的 checkpoint”和“用于发布的最终模型”职责分离。

    14.2 优化 tokenization 吞吐

    当前每次迭代都对原始故事执行 Python 层 tokenizer.encode。 对 30M 模型而言，模型计算相对便宜，CPU tokenization 更容易成为瓶颈。 预分词和预 packing 通常能显著提高 GPU 利用率。

    14.3 增加训练完成断言与评估摘要

    可以在训练结束后记录并验证：

    • trainer.state.global_step == MAX_STEPS。
    • 最终 train loss、eval loss、perplexity 与峰值显存。
    • 固定 prompt 集的生成样本，便于比较不同 checkpoint。
    • 模型与 tokenizer 的配置、Git commit、依赖版本和训练设备。

    14.4 把评估与发布解耦

    当前 notebook 只展示单个 prompt 的定性生成。更完整的流程可增加： validation perplexity、多个固定 prompt、重复率、故事结束率， 以及不同 seed 下的稳定性测试。只有评估通过的 checkpoint 才上传为正式模型。

    16. 一句话总结

    tinylm.ipynb 展示了一条结构完整的小语言模型训练链路： 用 TinyStories 控制任务难度，用 8K 自训练 tokenizer 控制 embedding 成本， 用 GQA、SwiGLU、RoPE 和 RMSNorm 组成现代 Qwen3 decoder， 再通过连续 packing、梯度累积、流式数据和 Drive checkpoint 在有限 Colab 资源上进行可恢复预训练。

    其最重要的工程取舍是：模型虽支持 1024 上下文，但训练使用 512； 数据虽是故事级样本，但训练使用无 padding 的连续 token blocks； 模型虽不到 30M 参数，但仍保留现代 LLM 的关键结构。
