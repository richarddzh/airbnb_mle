一句话概括

SageServe 不把 LLM 自动伸缩看成单一阈值问题，而是把秒/分钟级路由与排队、小时级流量预测和容量规划、实时显存反馈纠偏组合成一个闭环：用可延迟的 NIW 请求填平交互式业务的 GPU 谷期，再用 ARIMA + ILP 提前配置跨区域、多模型容量，从而在保持尾延迟的同时最多减少约 25% GPU-hours。

为什么 LLM 自动伸缩特别难

CPU Web 服务通常可以在秒级启动容器，LLM 服务却需要分配 GPU VM、复制模型结构和几十到数百 GB 权重、初始化并更新上游路由。论文给出的生产量级是：同区域已有模型权重时约需 10 分钟，权重不在本地时可达 2 小时。这意味着“看到负载升高再扩容”往往已经太迟。

论文 Fig. 1 用单实例 4,000 TPS 举例：Reactive 策略在第 15 分钟触发扩容，但实例第 20 分钟才就绪，中间 5 分钟持续欠配；若为了保险把有效容量按 3,500 TPS 估算，又会被短暂流量波动误导，造成过配。核心矛盾是：

阈值设得激进  → 扩容太晚 → SLA 违约
阈值设得保守  → 短暂尖峰触发扩容 → GPU 浪费
模型切换很慢  → 错误决策的代价持续数十分钟甚至数小时

系统架构：一个多时间尺度控制回路

1. Load Predictor每小时预测各模型、各区域的 IW 输入 TPS
2. ILP Optimizer计算跨区域、跨模型的实例增减量
3. Autoscaler结合显存与预测偏差执行扩缩容
4. Region Router按实时负载把 IW 路由到可用区域
5. Queue + Scheduler用空闲容量执行 NIW，并按 SLA 排批

这个设计的关键不是 ARIMA 或 ILP 本身，而是不同控制动作匹配不同时间尺度：

时间尺度控制动作解决的问题
请求级跨区域路由、区域内最短队列、实例内 batching吸收秒级抖动，减少局部负载倾斜。
分钟级NIW Queue Manager、Spot 回收、显存阈值纠偏利用临时余量并快速应对预测误差。
小时级ARIMA 预测 + ILP 容量规划在模型加载耗时之前提前配置容量。

交互式请求如何路由

  1. Global Region Router 查找目标模型有效显存利用率低于 70% 的区域，并按网络距离等偏好选择；如果所有区域都超过阈值，就选利用率最低的区域。
  2. 区域内 Model Router 选择负载最低的 deployment。
  3. deployment 内按剩余待处理 token 最少选择实例，即 token-aware 的 Join-the-Shortest-Queue。
  4. 实例调度器在显存允许范围内组 batch，优先处理高优先级与临近 deadline 的请求。

“有效显存利用率”会扣除模型权重占用，主要反映请求 KV Cache 的压力，因此比 GPU 总显存利用率更接近实时 serving load。

NIW 如何填谷且不伤害 IW

规则行为目的
endpoint 利用率 < 60%Queue Manager 每次释放 1 个 NIW 请求。保守使用余量。
endpoint 利用率 < 50%每次释放 2 个 NIW 请求。低谷时提高吞吐。
NIW 年龄 < 10 小时优先级为 1，排在 IW 之后。避免干扰交互请求。
NIW 年龄 > 10 小时提升为优先级 0，与 IW 同级。通过 aging 防止饥饿并满足 24 小时 deadline。
NIW 请求过大拆成固定大小 job。避免单个长请求占满 batch。

预测、优化与自动伸缩

ARIMA 预测如何进入决策

每个模型 × 每个区域：
  1. 用过去流量训练 ARIMA
  2. 预测未来 1 小时输入 TPS
  3. 取预测窗口内最大值
  4. 加安全余量 β = 过去 1 小时 NIW 负载 × 10%
  5. 交给 ILP 计算实例增减量
  6. Autoscaler 决定何时真正执行

论文比较了 Moving Average、TVAR、HMM 与 ARIMA。Moving Average 虽快但不准确；TVAR/HMM 可能更准，但训练更慢。作者最终选择 60 分钟训练窗口的 ARIMA，以较低预测开销换取“足够好”的周期性预测。下一小时预测约耗时 0.7 秒，ILP 在四模型、三区域、单 GPU 类型下平均约 1.41 秒，远低于一小时控制周期（Appendix B、Fig. 17）。

ILP 在优化什么

令 n[i,j,k] 为区域 j 中、GPU 类型 k 上模型 i 的当前实例数，δ[i,j,k] 为需要增加或减少的实例数，θ[i,k] 为单实例 TPS 容量，ρ[i,j,w] 为未来窗口 w 的预测需求，ε 为必须在本地满足的峰值比例。

本地容量约束：
Σk (n[i,j,k] + δ[i,j,k]) × θ[i,k]
  ≥ max_w ε × ρ[i,j,w]

全局容量约束：
Σj Σk (n[i,j,k] + δ[i,j,k]) × θ[i,k]
  ≥ max_w Σj ρ[i,j,w]

合法缩容约束：
δ[i,j,k] ≥ -n[i,j,k]

目标：
minimize  VM 调整成本 + 模型加载成本

本地约束保证每个区域能独立承担一部分峰值，其余需求允许跨区路由；全局约束保证所有区域的总容量足够。目标函数惩罚 VM 获取与模型加载的浪费，避免为了短暂流量频繁换模型。严格来说，它不是直接最大化 SLA utility；SLA 主要由容量约束、在线路由和实例调度共同保证。

扩展到 20 个模型、20 个区域、5 种 GPU 时，论文报告 ILP 求解约 33 秒，对小时级控制仍然可接受。

3. 成本数字要正确理解

论文按 Azure H100 cluster 98.32 美元/小时，以及“85 instance-hours/天 × 3 模型 × 4 区域 × 7 天”线性外推，估算每周约节省 60 万美元、每月最高约 250 万美元。这是基于公开价格和扩展假设的潜在节省，不是实际生产账单审计。

注意两个不同口径：正文 §7.2.4 报告扩容期间浪费的 GPU cycles 下降约 70%；摘要和贡献项报告自动伸缩浪费或 VM cold-start 最高下降 80%。两者测量对象与表述并不完全相同，不应合并成同一个结论。

这篇论文真正重要的思想

  1. Autoscaling 应是多时间尺度控制，而不是一个阈值。快控制负责路由与排队，慢控制负责模型放置和 GPU 容量，在线反馈负责纠偏。
  2. 预测的价值是提前量，不是绝对准确。模型加载需要 10 分钟到 2 小时，只要预测能捕捉趋势，就能提前做有价值的决策；LT-UA 再处理预测误差。
  3. 可延迟负载是提高 GPU 利用率的天然“蓄水池”。NIW 不只是低优先级请求，而是可以吸收 IW 低谷容量的调节资源。
  4. 容量规划必须跨区域、跨模型联合看。单区域优化会忽略低延迟跨区网络和模型容量不均衡，单模型优化会忽略重部署机会成本。
  5. TPS 比 RPS 更接近 LLM 成本。RAG 等应用输入长度差异巨大，相同请求数可能产生完全不同的 KV Cache、prefill 和 decode 压力。

局限为什么重要生产落地需要补什么

如果要在真实平台复现

  1. 先建立 model × engine × GPU 的 TPS/TTFT 容量曲线，并持续校准。
  2. 统一 IW/NIW 资源池，但为 IW 设置硬容量底线；NIW 必须支持 chunking、deadline aging 和快速暂停。
  3. 每小时预测模型与区域级输入 TPS，同时保留 P50/P90/P99 或置信区间，而不只输出点预测。
  4. ILP 输出目标容量；执行层采用类似 LT-UA 的“预测目标 + 显存阈值 + 实际 TPS 偏差”控制。
  5. 预置热点模型权重，将跨模型重部署从约 2 小时压到约 10 分钟。
  6. 监控预测误差、有效显存、排队 token、TTFT/TBT/E2E、NIW deadline、冷启动时间、Spot 回收时间和跨区网络延迟。
  7. 先 shadow，再单模型/单区域灰度；成本收益用真实内部价格重新计算。

最终评价

SageServe 的贡献不是发明了新的预测模型，而是把生产 LLM serving 中几个常被分开处理的问题——跨区路由、异步队列、模型放置、GPU 扩缩容、Spot 复用和多 SLA batching——放进同一个控制框架。它最值得借鉴的工程方法是：利用预测获得冷启动所需的提前量，但永远让实时系统信号保留纠错权。

从研究证据看，统一资源池是最稳健、最直接的收益来源；ARIMA + ILP 则进一步降低小时级容量浪费；LT-UA 展示了如何避免“预测驱动系统被预测绑架”。同时，成本节省和 SLA 结论主要来自生产轨迹回放与模拟，真正上线仍需对模型容量曲线、网络长尾、异常流量和业务级 deadline 做严格校准。

数据与结论主要来自论文 v3 的 Sections 1–7、9，Figures 1–17，Tables 1–2 及 Appendices A–B。报告中的美元节省为论文外推估算；70% 与 80% 两个浪费降幅按论文不同口径分别呈现。
