      Request Batching 与可观测性实验

      Batching 的目标通常是用少量延迟换取更高吞吐。正确实验必须有基线、并发负载和指标证据；只看到 GPU utilization 变高，不能证明请求真的被合批。

      四种“batch”不要混淆

      机制谁创建适合关键特点
      Client static batch客户端客户端本来就有一批样本一个请求内 shape 首维大于 1
      Triton dynamic batchingTriton scheduler无状态 tensor 模型把多个独立请求合成一次 backend execution
      Sequence batchingTriton scheduler序列状态必须保持的模型按 sequence/correlation ID 调度
      vLLM continuous batchingvLLM engineautoregressive LLM请求可在不同 token step 加入/退出执行集合

      Dynamic batching 工作方式

      sequenceDiagram participant A as Request A participant B as Request B participant C as Request C participant Q as Triton Queue participant G as GPU Instance A->>Q: t=0 B->>Q: t=40µs C->>Q: t=70µs Note over Q: max_queue_delay 内等待
      形成 batch=3 Q->>G: 一次 backend execution G-->>Q: batched outputs Q-->>A: response A Q-->>B: response B Q-->>C: response C

      启用默认 dynamic batching：

      max_batch_size: 8
dynamic_batching {}

      允许最多等待 200 微秒来收集更多请求：

      dynamic_batching {
  max_queue_delay_microseconds: 200
}

      官方建议大多数模型不要先设置 preferred_batch_size；默认让调度器尽可能组成不超过 max batch 的大批。只有特定 batch size 明显更快（例如 TensorRT optimization profile）时才优先使用。

      关键配置如何影响结果

      配置调大后的可能收益代价/风险
      max_batch_size单次执行容纳更多样本模型必须支持动态首维；显存与延迟可能增加
      max_queue_delay_microseconds低流量也更容易凑批请求主动等待，tail latency 上升
      preferred_batch_size命中特定高效 profile错误配置会增加等待且未必更快
      instance_group.count并发执行、重叠传输和计算额外显存；可能妨碍单实例凑大批
      客户端 concurrency给 scheduler 足够在途请求过高会积压并恶化 p95/p99

      完整对照实验

      建议用普通小型 ONNX/TorchScript 模型，而不是先用 LLM。RTX 4070 和 CPU 机器都能完成；CPU 下数值不同，但方法相同。

      1. 准备基线配置。保持 max_batch_size: 8，暂时移除 dynamic_batching，model instance 为 1。
      2. 预热。先发送若干请求，避免把模型加载、JIT 或 cache 冷启动计入稳态。
      3. 测无 batching。用 perf_analyzer 做 concurrency 1、2、4、8，记录吞吐和 p95。
      4. 启用默认 dynamic batching。仅添加 dynamic_batching {}，重启或 reload 模型，重复相同负载。
      5. 加 queue delay。测试 100、200、500 微秒，找到延迟预算内的最高吞吐。
      6. 读 metrics。比较 inference count / execution count，计算平均执行 batch size。
      7. 最后才测试 instance count。将实例从 1 改 2，观察收益是否值得额外显存和延迟。

      使用 perf_analyzer

      SDK 镜像包含客户端工具。Windows/WSL2 上不要依赖 --net=host 的跨平台细节，最稳妥是将 server 与 SDK 放入同一个 Docker network。

      创建网络并启动 server（示意） 
      docker network create triton-net

docker run --name triton --rm --network triton-net \
  --gpus=1 \
  -p 8000:8000 -p 8001:8001 -p 8002:8002 \
  -v "$PWD/model_repository:/models" \
  nvcr.io/nvidia/tritonserver:<xx.yy>-py3 \
  tritonserver --model-repository=/models
      另一终端：从 SDK 容器压测 
      docker run --rm --network triton-net \
  nvcr.io/nvidia/tritonserver:<xx.yy>-py3-sdk \
  perf_analyzer -m <model-name> \
    -u triton:8001 \
    -i grpc \
    --percentile=95 \
    --concurrency-range 1:8

      输入数据：真实模型通常需要用 --input-data 指定符合 tensor shape/type 的 JSON。先运行 perf_analyzer --help 并对照当前版本文档，不要假设随机输入适合所有模型。

      Prometheus 指标如何证明合批

      curl -s localhost:8002/metrics > metrics.txt
grep 'nv_inference_.*{.*model="<model-name>"' metrics.txt

      官方 metrics 文档给出三个重要计数：

      计数含义
      Request Count客户端请求数
      Inference Count请求中的样本总数；batch-8 请求贡献 8
      Execution Countbackend model instance 实际执行次数
       
      平均执行 batch size ≈ Inference Count / Execution Count

      例：发送 100 个 batch-1 请求，最终 inference count=100、execution count=25，则平均每次 backend execution 处理约 4 个样本。这是动态合批的直接聚合证据。

      延迟拆分

      • queue duration：调度等待，包括为合批主动等待和实例繁忙等待。
      • compute input：输入准备和传输。
      • compute infer：核心模型执行。
      • compute output：输出准备和复制。
      • pending request count：已进入 Triton core 但尚未由 backend instance 开始执行的请求。

      Trace 精确定位

      启动时采集前 100 个请求的时间戳：

      tritonserver --model-repository=/models \
  --trace-config triton,file=/tmp/trace.json \
  --trace-config triton,log-frequency=50 \
  --trace-config rate=1 \
  --trace-config level=TIMESTAMPS \
  --trace-config count=100

      Trace 中可看到 REQUEST_START、QUEUE_START、COMPUTE_START、COMPUTE_END、REQUEST_END。生产环境不要无界开启高采样率，尤其不要随意记录 tensor 内容。

      vLLM 如何观察 batching

      vLLM 生成请求长度不同，不能用普通 fixed-shape dynamic batch 的思维解释。建议：

      • 使用当前 Triton release 提供的 GenAI-Perf，对固定 input/output token 长度和不同 concurrency 做对照。
      • 记录 time to first token、inter-token latency、request latency、tokens/s。
      • 同时查看 vLLM engine 暴露的 running/waiting requests、KV cache 使用等版本相关指标。
      • 保持模型、prompt 长度、output token、sampling 参数一致，只改变并发。

      如何判断优化成功

      现象判断
      吞吐提高，p95 在预算内，平均 batch 增大成功
      吞吐几乎不变，queue latency 大幅增加delay 过高或模型不从 batching 受益
      GPU 已满载，增加 instance 只增延迟一个实例已足够，回退
      concurrency=1 看不到合批正常；没有同时在途请求可合并
      vLLM 吞吐提高但 Triton execution 指标难解释应结合 engine/token 指标，不能套用普通 dynamic batch 结论
