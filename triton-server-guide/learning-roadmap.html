      分阶段学习路线与验收清单

      不要在第一天同时解决 WSL、Docker、Triton、LLM、量化和 batching。下面每一阶段只有一个主要变量，并给出可验证的完成标准。

      路线总览

      flowchart LR S0["0 环境
      GPU/CPU + Docker"] --> S1["1 Server
      health + metrics"] S1 --> S2["2 小模型
      repository + infer"] S2 --> S3["3 Batching
      baseline + concurrency"] S3 --> S4["4 PyTorch
      TorchScript"] S4 --> S5["5 vLLM
      单卡小 LLM"] S5 --> S6["6 观测
      trace + GenAI perf"]

      Stage 0：环境验证

      目标：证明执行环境可用，不启动 Triton。

      RTX 4070 路径

      # Windows PowerShell
nvidia-smi
wsl -l -v

# WSL2 Ubuntu
nvidia-smi
docker run --rm --gpus all ubuntu nvidia-smi

      CPU-only 路径

      docker version
docker run --rm ubuntu uname -a

      成功标准：GPU 路径在三层都看见 RTX 4070；CPU 路径能正常运行 Linux 容器。

      Stage 1：空仓库与 Server 生命周期

      目标：理解容器、端口、live/ready、日志和 metrics。

      mkdir -p ~/triton-lab/model_repository
cd ~/triton-lab

docker run --rm \
  -p 8000:8000 -p 8001:8001 -p 8002:8002 \
  -v "$PWD/model_repository:/models" \
  nvcr.io/nvidia/tritonserver:<xx.yy>-py3 \
  tritonserver --model-repository=/models

      成功标准：health ready 返回 200；metrics 端点返回 Prometheus 文本；你能解释三个端口。

      Stage 2：CPU add/sub 模型

      目标：跑通本手册模型仓库页面的 Python backend 示例。

      • 创建 config.pbtxt 和 1/model.py。
      • 模型状态为 READY。
      • curl 推理返回正确加减结果。
      • 故意改错 tensor name，观察日志，再恢复。

      成功标准：能从日志定位一次配置错误，而不是只会重启容器。

      Stage 3：动态批处理实验

      目标：用数据证明 request batching。

      1. 关闭 dynamic batching，测 concurrency 1/2/4/8。
      2. 启用 dynamic_batching {}，重复测量。
      3. 记录 throughput、p95、queue duration。
      4. 读取 inference count 和 execution count，计算平均 batch size。
      5. 加入 100–500µs delay，观察吞吐/延迟边界。

      成功标准：能解释为什么 concurrency=1 很难观察 server-side dynamic batching，以及为什么更高吞吐可能伴随更高延迟。

      Stage 4：TorchScript 模型

      目标：理解 PyTorch eager 模型与 Triton PyTorch backend 接口的区别。

      • 导出一个最小 TorchScript 模型。
      • 先在 CPU instance 加载，再改为 RTX 4070 GPU instance。
      • 核对 input/output 命名和 batch dimension。
      • 观察 CPU/GPU 的显存与延迟，但不急于做性能结论。

      成功标准：能解释为什么普通 safetensors 不能直接作为 LibTorch model file。

      Stage 5：RTX 4070 上的 vLLM

      目标：部署显存可容纳的小型 instruct LLM。

      1. 从与 Triton 版本相同的 vLLM backend release branch 复制 sample repository。
      2. 选择当前 vLLM 明确支持的 0.5B–3B 模型。
      3. 设置 tensor parallel=1、max model length=2048、GPU utilization 约 0.80。
      4. 挂载 Hugging Face cache，启动并观察 nvidia-smi。
      5. 先单请求成功，再提高到 concurrency 2/4。

      成功标准：模型 READY；能得到完整或流式文本；不会把 vLLM continuous batching 误叫作 Triton dynamic batching。

      Stage 6：服务端观测

      目标：把性能问题拆成接入、排队、输入、推理、输出和生成 token。

      • 普通模型：perf_analyzer + Prometheus + Triton trace。
      • LLM：GenAI-Perf（当前 release 支持时）+ time to first token + inter-token latency + tokens/s。
      • 固定输入长度、输出长度和 sampling 参数，逐级改变 concurrency。
      • 保存每轮模型、配置、容器版本、驱动版本和测试命令。

      最终能力检查

      问题合格答案应包含
      Triton 是什么？协议、模型仓库、per-model scheduler、backend、metrics；不是训练框架
      一张 4070 能学吗？能；12GB 限制模型、上下文和并发，不限制 server 核心概念
      PyTorch LLM 怎么部署？区分 TorchScript LibTorch、Python backend 与 vLLM/TensorRT-LLM
      如何证明合批？并发负载 + inference/execution count + latency/throughput 对照
      Windows 为什么用 WSL2？Linux 容器、GPU-PV、Docker Desktop WSL2 GPU 官方支持
      CPU 可以做什么？server/repository/protocol/batching/metrics；不代表 GPU LLM 性能

      停止条件与回退策略

      • 容器看不到 GPU：停止模型调试，回到环境验证。
      • 小 add/sub 模型未成功：停止 LLM 部署，先修仓库和网络。
      • LLM OOM：减上下文、并发、模型规模；不要先增加 swap 期待解决 GPU OOM。
      • 吞吐测试不稳定：增加 warmup 和测量时间，固定输入，关闭其他 GPU 程序。
      • 版本不兼容：让 Triton server、SDK 和 backend sample 使用同一年月 release。
