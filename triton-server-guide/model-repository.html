      Quickstart 与 Model Repository

      Triton 的核心不是一条启动命令，而是“模型仓库契约”：目录名决定模型名，数字子目录决定版本，config.pbtxt 决定 backend、tensor 形状、batching 和实例。

      先理解目录契约

      model_repository/
├── add_sub/
│   ├── config.pbtxt
│   └── 1/
│       └── model.py
└── my_torch_model/
    ├── config.pbtxt
    ├── 1/
    │   └── model.pt
    └── 2/
        └── model.pt
      • add_sub 是请求中的 model name。
      • 1、2 必须是数字版本目录，不是随意分类目录。
      • 版本目录中的文件名和结构由 backend 决定。
      • config.pbtxt 位于模型目录根部，不在版本目录内。
      • Triton 可从多个 repository、本地目录、S3、GCS、Azure Storage 读取模型；入门只用本地挂载。

      推荐的 Windows 实验目录

      在 WSL2 的 Linux home 中创建，不要优先放在 C:\ 对应的 /mnt/c。Linux 文件系统通常有更自然的权限、链接和 I/O 行为。

      mkdir -p ~/triton-lab/model_repository
cd ~/triton-lab
pwd
# 预期类似 /home/<user>/triton-lab

      实验 A：创建 CPU/GPU 都能运行的 Python backend 模型

      这个模型只做加减法，不依赖 GPU。它特别适合 CPU 机器，也适合先证明 Triton server、仓库和客户端链路正确。

      WSL2 / Linux：创建目录 
      mkdir -p ~/triton-lab/model_repository/add_sub/1
cd ~/triton-lab
      model_repository/add_sub/config.pbtxt 
      name: "add_sub"
backend: "python"
max_batch_size: 8

input [
  { name: "INPUT0" data_type: TYPE_FP32 dims: [ 4 ] },
  { name: "INPUT1" data_type: TYPE_FP32 dims: [ 4 ] }
]

output [
  { name: "OUTPUT0" data_type: TYPE_FP32 dims: [ 4 ] },
  { name: "OUTPUT1" data_type: TYPE_FP32 dims: [ 4 ] }
]

dynamic_batching {}
      model_repository/add_sub/1/model.py 
      import numpy as np
import triton_python_backend_utils as pb_utils


class TritonPythonModel:
    def execute(self, requests):
        responses = []
        for request in requests:
            input0 = pb_utils.get_input_tensor_by_name(
                request, "INPUT0").as_numpy()
            input1 = pb_utils.get_input_tensor_by_name(
                request, "INPUT1").as_numpy()

            output0 = pb_utils.Tensor(
                "OUTPUT0", (input0 + input1).astype(np.float32))
            output1 = pb_utils.Tensor(
                "OUTPUT1", (input0 - input1).astype(np.float32))
            responses.append(pb_utils.InferenceResponse(
                output_tensors=[output0, output1]))
        return responses

      为什么能 batching：max_batch_size: 8 表示 Triton 会在配置中的 dims: [4] 前添加 batch 维度。Python backend 的 execute 接收 request 列表；每个 tensor 自身也会带 batch 维。

      启动 server：GPU 与 CPU 两条命令

      RTX 4070 12GB / WSL2 GPU

      cd ~/triton-lab
export TRITON_VERSION=<xx.yy>

docker run --gpus=1 --rm \
  --shm-size=1g \
  -p 8000:8000 -p 8001:8001 -p 8002:8002 \
  -v "$PWD/model_repository:/models" \
  nvcr.io/nvidia/tritonserver:${TRITON_VERSION}-py3 \
  tritonserver --model-repository=/models

      CPU-only

      cd ~/triton-lab
export TRITON_VERSION=<xx.yy>

docker run --rm \
  --shm-size=1g \
  -p 8000:8000 -p 8001:8001 -p 8002:8002 \
  -v "$PWD/model_repository:/models" \
  nvcr.io/nvidia/tritonserver:${TRITON_VERSION}-py3 \
  tritonserver --model-repository=/models

      两条命令的唯一关键差异是 GPU 路径有 --gpus=1。当前 add/sub 模型仍在 CPU 执行；GPU 暴露只是为后续 GPU 模型准备。

      逐项解释启动参数

      参数含义常见问题
      --gpus=1向容器暴露一张 GPU不是“使用编号为 1 的 GPU”；单卡机器表示数量为 1
      -p 8000:8000映射 HTTP端口被占用时更换左侧宿主端口
      -v "$PWD/...:/models"把宿主仓库挂进容器路径错误时 server 看不到模型
      ...:<xx.yy>-py3带 Python backend 的 Triton 镜像必须换成 NGC 中存在的标签
      --model-repository=/models容器内仓库路径它对应 volume 的右侧路径

      验证 server 和模型

      WSL2 另开一个终端 
      curl -i localhost:8000/v2/health/live
curl -i localhost:8000/v2/health/ready
curl -i localhost:8000/v2/models/add_sub/ready
curl localhost:8000/v2/models/add_sub/config

      前三个检查都应返回 200。若 server ready 但模型不 ready，问题通常在仓库结构、配置或 backend 文件。

      发送 HTTP 推理请求

      curl -s localhost:8000/v2/models/add_sub/infer \
  -H "Content-Type: application/json" \
  -d '{
    "inputs": [
      {
        "name": "INPUT0",
        "shape": [1, 4],
        "datatype": "FP32",
        "data": [1, 2, 3, 4]
      },
      {
        "name": "INPUT1",
        "shape": [1, 4],
        "datatype": "FP32",
        "data": [10, 20, 30, 40]
      }
    ],
    "outputs": [
      {"name": "OUTPUT0"},
      {"name": "OUTPUT1"}
    ]
  }'

      应得到加法结果 [11,22,33,44] 和减法结果 [-9,-18,-27,-36]。请求 shape 为 [1,4]，其中第一个 1 是 batch size。

      config.pbtxt 的最低理解

      字段作用
      backend / platform选择模型执行 backend/平台
      max_batch_size0 表示 Triton 不使用首维 batching；大于 0 表示最大 batch
      input/outputtensor 名、数据类型、每个样本的维度
      dynamic_batching为无状态模型启用动态合批
      instance_group指定实例数量和 CPU/GPU 类型
      model_transaction_policy声明 decoupled 等请求响应语义

      常见错误排查

      现象检查
      模型未出现在启动表格检查 volume 左侧路径、模型目录层级、数字版本目录
      UNAVAILABLE从日志找到第一条具体 backend/config 错误，不只看最后的 server not ready
      shape mismatch区分 config 的 per-sample dims 与请求中的 batch + dims
      端口访问失败确认容器仍在运行、端口映射、Windows 防火墙和端口占用
      GPU model 加载失败先验证容器内 nvidia-smi，再检查驱动、CUDA 兼容和显存
