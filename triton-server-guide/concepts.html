      Triton 核心概念与架构

      先把 Triton 看作“模型推理的统一服务进程”：客户端不直接操作模型文件，而是向 Triton 发请求；Triton 再按模型配置完成排队、合批、选择实例和调用 backend。

      Triton 做什么

      能力说明你能观察什么
      统一协议HTTP/REST、gRPC，以及嵌入式使用的 C API请求、响应、健康检查
      模型生命周期从一个或多个 model repository 加载、卸载、查询版本READY/UNAVAILABLE、加载错误
      每模型调度模型可分别使用默认、dynamic 或 sequence scheduler队列时间、execution count
      多后端TensorRT、ONNX Runtime、PyTorch、Python、vLLM 等相同协议访问不同框架
      实例管理一个模型可以有一个或多个 CPU/GPU instance并行执行与显存占用
      可观测性Prometheus metrics、trace、日志、性能工具吞吐、延迟、GPU、batch size

      Triton 不做什么

      • 不训练模型：训练、微调、数据准备仍由 PyTorch、Transformers 等完成。
      • 不自动让任意模型变快：模型必须与 backend 兼容，batching 和 instance 数要通过测量调优。
      • 不是模型格式：config.pbtxt 描述服务配置，真正模型仍是 TorchScript、ONNX、TensorRT plan 或 backend 所需文件。
      • 不是 vLLM 的替代品：vLLM 是 LLM execution engine；Triton 可以把它包装为统一服务的一种 backend。
      • 不是 Kubernetes：Triton 可被 Kubernetes 管理，但自身不负责跨主机部署、服务发现和高可用。

      核心对象

      Model repository

      文件系统或对象存储中的模型集合。启动参数 --model-repository=/models 告诉 Triton 去哪里找模型。每个模型一个目录，每个版本一个数字目录。

      Backend

      把 Triton 的标准请求转换成某种执行引擎调用的适配层。例如 PyTorch backend 使用 LibTorch 执行 TorchScript，vLLM backend 把生成请求放入 AsyncEngine。

      Scheduler 与 batcher

      每个模型有自己的调度器。无状态模型常用 dynamic batcher 合并同时到达的请求；有状态序列模型可用 sequence batcher 保持同一序列的相关性。

      Model instance

      模型的一份可执行副本。默认通常为一个实例；增加实例可能提高重叠执行能力，也会增加显存占用。实例多不等于性能一定更高。

      一次请求的生命周期

      sequenceDiagram participant C as Client participant F as HTTP/gRPC Frontend participant S as Per-model Scheduler participant B as Backend participant G as GPU C->>F: Infer request + tensor/text F->>S: 标准化为 Triton request Note over S: 排队；可选 dynamic batching S->>B: 一批 requests B->>G: H2D / kernel / runtime G-->>B: output B-->>F: Triton response F-->>C: HTTP/gRPC response Note over F,G: metrics 计数；可选 trace 时间戳
      1. 接入。Frontend 解析 HTTP/gRPC，把协议字段转换为 Triton 内部请求。此时还没有执行模型。
      2. 排队。请求进入对应模型的 scheduler。若实例忙，请求处于 pending；若启用 dynamic batching，调度器尝试合并兼容请求。
      3. 执行。批次交给一个可用 model instance，backend 调用框架或 engine。
      4. 返回。输出被拆回各请求并经 frontend 返回；decoupled 模型则可能一请求多响应并流式返回。

      端口与 API

      默认端口用途入门验证
      8000HTTP/REST inference、health、model APIcurl localhost:8000/v2/health/ready
      8001gRPC inference 与管理 API使用 Triton client SDK
      8002Prometheus 文本指标curl localhost:8002/metrics

      live 与 ready：live 表示 server 进程活着；ready 表示 server 已准备接收推理。模型还有 /v2/models/<model>/ready。生产探针应按目标选择，不能只看容器进程存在。

      与 FastAPI + 模型代码的区别

      维度直接 FastAPITriton
      灵活性任意 Python 逻辑最灵活受 backend 接口与模型配置约束
      协议自行设计统一的 V2 inference protocol
      批处理自行写队列与并发控制普通模型可配置 dynamic batching
      多框架自行维护不同 runtime统一管理多 backend
      可观测性自行埋点内置请求/GPU metrics 与 tracing
      入门成本小 demo 较低需要理解仓库和 config.pbtxt

      适合 Triton 的场景

      • 希望用统一协议托管 ONNX、TensorRT、TorchScript、Python 或 LLM engine。
      • 需要动态批处理、多模型实例、标准指标、模型版本和显式配置。
      • 希望把模型服务层与业务 API 层分离。

      如果只是个人脚本调用一次模型，Triton 可能过重；如果目标正是学习“推理 server 如何调度请求”，Triton 非常合适。
