      用 vLLM backend 部署本地 LLM

      可以。Triton 官方 vLLM backend 把请求放入 vLLM AsyncEngine，由 vLLM 负责 inflight/continuous batching 和 paged attention。RTX 4070 12GB 适合小模型、量化模型和低并发实验。

      适合你的基线：Windows 11 + WSL2 + RTX 4070 12GB；先选约 0.5B–3B 的 instruct 模型或 vLLM 明确支持的量化模型，将最大上下文控制在 2K–4K，初始并发设 1–2。确认稳定后再增加。

      Triton 与 vLLM 的职责边界

      flowchart LR C["客户端请求"] --> T["Triton frontend
      协议 · health · metrics"] T --> B["vLLM backend
      Python-based adapter"] B --> E["vLLM AsyncEngine
      continuous batching
      paged attention · KV cache"] E --> G["RTX 4070 12GB"] R["model.json
      engine arguments"] --> E
      层主要职责
      Triton统一服务端口、模型仓库与生命周期、协议、模型级 metrics/trace、部署集成
      vLLM backend把 Triton request/response 转换为 vLLM engine 调用
      vLLM AsyncEnginetoken 调度、KV cache、paged attention、inflight/continuous batching

      关键区别：不要把普通模型的 Triton dynamic_batching {} 与 vLLM 的 continuous batching 当成同一个机制。官方 vLLM backend 会尽快把请求交给 AsyncEngine，生成阶段的批调度由 vLLM 完成。

      容器选择

      官方预构建 vLLM 镜像标签形式为：

      nvcr.io/nvidia/tritonserver:<xx.yy>-vllm-python-py3

      该镜像从 Triton 23.10 起提供。使用前在 NGC 查询实际存在的标签，并阅读对应 release notes。不要把普通 -py3 镜像与 vLLM 镜像混淆。

      建立模型仓库

      官方仓库提供 sample model repository。不同 release 的字段可能变化，因此最可靠流程是克隆与容器版本相同的 release branch，再修改样例，而不是凭记忆手写所有字段。

      cd ~/triton-lab
export TRITON_VERSION=<xx.yy>

git clone --branch r${TRITON_VERSION} --depth 1 \
  https://github.com/triton-inference-server/vllm_backend.git

cp -r vllm_backend/samples/model_repository/vllm_model \
  model_repository/

      典型结构如下：

      model_repository/
└── vllm_model/
    ├── config.pbtxt
    ├── model.json
    └── 1/
        └── model.py

      配置 model.json

      model.json 是传给 vLLM engine 初始化参数的键值字典。实际字段以你所用 release 的 sample 和 vLLM argument 文档为准。概念示例如下：

      {
  "model": "Qwen/Qwen2.5-1.5B-Instruct",
  "dtype": "auto",
  "tensor_parallel_size": 1,
  "max_model_len": 4096,
  "gpu_memory_utilization": 0.85
}

      模型名只是示例：部署前必须在当前 vLLM 的 supported models 页面确认架构和量化格式。若模型需要 Hugging Face 授权，还需先接受许可并提供 token。

      RTX 4070 12GB 参数起点

      参数建议起点原因
      tensor_parallel_size1只有一张 GPU
      gpu_memory_utilization0.80–0.85给 CUDA、桌面与碎片保留余量
      max_model_len2048 或 4096KV cache 随上下文和并发增长
      并发1 起步，再到 2/4先确认稳定和延迟，再观察连续批处理
      模型规模0.5B–3B 优先让 12GB 显存有足够 KV cache 与 runtime 空间

      挂载 Hugging Face cache 并启动

      cd ~/triton-lab
mkdir -p ~/.cache/huggingface

docker run --gpus=1 --rm \
  --shm-size=2g \
  -p 8000:8000 -p 8001:8001 -p 8002:8002 \
  -v "$PWD/model_repository:/models" \
  -v "$HOME/.cache/huggingface:/root/.cache/huggingface" \
  -e HF_TOKEN="${HF_TOKEN:-}" \
  nvcr.io/nvidia/tritonserver:${TRITON_VERSION}-vllm-python-py3 \
  tritonserver --model-repository=/models

      缓存挂载避免每次销毁容器都重新下载权重。不要把 token 写进 HTML、脚本、镜像或 Git；只通过环境变量/安全凭据传递。

      加载阶段要观察什么

      1. 下载。首次运行可能长时间下载；看网络、磁盘和 cache，而不是误判 server 死亡。
      2. 分配显存。用另一终端运行 watch -n 1 nvidia-smi，观察权重和 KV cache 分配。
      3. READY。curl -i localhost:8000/v2/models/vllm_model/ready 必须返回 200。
      4. 请求。优先运行该 release sample 自带 client，因为 vLLM backend 的 input/output tensor contract 可能随版本演进。

      Streaming 与 decoupled mode

      LLM 会逐 token 生成。一请求一次完整响应适合最简测试；流式输出需要 backend 使用 decoupled transaction policy，使一个请求可以产生多个 response。客户端通常使用 gRPC streaming 或样例所定义的协议。

      model_transaction_policy {
  decoupled: true
}

      是否需要、如何配置，以当前 vLLM sample 的 config.pbtxt 为准。不要只添加这一行而忽略 client 和 output contract。

      12GB 显存常见 OOM 处理顺序

      1. 确认没有另一个模型/进程占 GPU。
      2. 把 model instance 保持为 1、tensor parallel 保持为 1。
      3. 降低 max_model_len 和并发。
      4. 降低 vLLM GPU memory utilization，给 runtime 留余量。
      5. 选择更小模型或当前 vLLM 支持的量化权重。
      6. 仍失败时检查量化 kernel 是否支持 RTX 4070（Ada）与当前 CUDA/vLLM 组合。

      CPU-only 能否运行 vLLM Triton 实验

      本手册不把 CPU-only vLLM 当作可靠入门基线。vLLM 的 CPU 支持、构建方式和性能限制随版本变化，而且预构建 Triton vLLM 容器主要面向 GPU。CPU 机器更适合用 Python/ONNX/PyTorch CPU backend 学习 server、repository、protocol 和 batching；LLM 生成改在 RTX 4070 环境完成。
