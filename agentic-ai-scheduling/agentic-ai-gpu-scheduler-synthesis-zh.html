从基础概念到可实现的调度流程

为什么 Agentic AI 可以被更好地调度到 GPU？

这不是一个“把请求送到最空闲 GPU”就能解决的问题。一次用户任务可能多次访问模型、等待工具、分叉执行，再汇合成最终答案。GPU 调度器如果只看到零散的模型调用，就会把已经花费很长时间的任务当成新请求，把并不紧急的计算和即将超时的响应一视同仁，并把显存容量、计算速度和通信成本混成一个“负载”数字。

如何区分事实与推导：本文对 AdaGen、USHER、AdaInf 的描述来自公开论文；本文提出的 Agentic 调度流程是一套教学与工程设计建议，不是三篇论文共同实现过的系统。所有标为“教学例子”的数字均为便于计算而设定，不能当作论文实验结果。

1. 先理解 GPU 到底在执行什么

1.1 Prefill 和 decode 不是同一种工作

把一个问题发给语言模型时，首先要处理已经给定的输入文本。经过分词后，输入变成一串 token。模型知道整段输入，因此可以在一次或若干次较大的计算中处理这些位置，这个阶段叫 prefill。随后模型逐步生成新 token，通常必须等前一个 token 被选出来才能继续下一个，这个阶段叫 decode。前者更像一次处理一批已经到齐的材料，后者更像沿着一条尚未写完的链逐步前进。

这种区别会改变 GPU 的效率。GPU 适合执行大量并行运算；较长 prefill 的矩阵乘法有机会摊薄权重读取成本，充分使用 Tensor Core。单个请求的 decode 每一步只产生很少的新 token，却仍需要读取相关权重和不断增长的注意力状态，因而经常受显存带宽限制。不过，“prefill 算力受限、decode 带宽受限”只是常见趋势，不是所有模型、batch size 和上下文长度都服从的定律。大 batch decode、长上下文注意力、MoE 通信都可能改变瓶颈，必须以实际测量为准。

1.2 为什么要把多个请求组成 batch

假设一台 GPU 同时服务十个人。若一次只为其中一人生成一个 token，权重和硬件可能无法被高效利用；把多人的计算合并到同一个 batch，可以共享一次大算子的开销，并提高并行度。问题是十个人不会同时开始、同时结束。Continuous batching 因此在每次执行步骤之间移除已完成请求，加入新请求，而不是等整批人都结束才开始下一批。

本文把这样的执行步骤称为 engine step。它不同于 Agent 的“第几轮工具调用”：一次 Agent 轮次中的 decode 可能跨越几百个 engine steps。混淆这两个尺度，很容易误以为按轮数排序等价于按 GPU 计算量排序。实际上，一轮生成一千个 token 和五轮各生成十个 token 的开销并不相同。

1.3 Chunked prefill 为什么与调度相关

如果一个新请求带来非常长的 prompt，把整个 prefill 一次塞进运行批次，可能让正在流式输出的其他请求很久得不到下一个 token。Chunked prefill 把长输入拆成若干较小片段，在多个 step 中逐步处理。它并没有消除输入计算，而是在“尽快启动新请求”和“不要阻断已有响应”之间提供一个可调旋钮。

片段太大，单步执行时间变长；片段太小，可能降低吞吐、增加调度和算子开销。所谓“优化调度”，很大一部分就是根据当前响应的 deadline、模型性能曲线和 GPU 状态选择这个片段大小，而不是为整个集群永久设置同一个值。AdaGen 将实例内部这种 token 排列称为 compute layout，并说明集群路由会改变最终布局。[A，§2–4]

这也不是只存在于论文里的抽象：vLLM 的优化文档说明，V1 在可用时默认启用 chunked prefill，通常先安排 decode，再利用 token budget 处理 prefill；减小或增大 max_num_batched_tokens 会改变 inter-token latency、TTFT 与吞吐的权衡。它为教学模型提供了实际引擎背景，但具体默认值随版本和配置变化，不应把文档里的示例参数当成所有 GPU 的最佳设置。[R1]

2. 为什么“GPU 很忙”不代表“用户更满意”

TTFT 是 time to first token，即某次调用从到达到第一个输出 token 的时间；它包含排队、输入处理以及首 token 生成的开销。TBT 是相邻输出 token 之间的时间间隔。TPOT 常被用来表示每个输出 token 的平均时间，但平均值可能掩盖流式响应中一次很长的卡顿，所以不能简单用平均 TPOT 代替尾部 TBT。

SLO 是服务承诺的目标，例如 95% 的请求应在某个时限内开始响应。这和“每一个请求都绝对不能晚于时限”的硬实时约束不是一回事。论文中的 SLO attainment 表示满足其指定判定规则的请求比例；goodput 则强调单位时间内完成的、满足质量或时限要求的有效工作。两者的分母和单位必须先读清楚。

教学例子：吞吐更大却服务更差

系统 A 每秒完成 100 个请求，其中 60 个满足 SLO；系统 B 每秒只完成 90 个，但有 81 个满足 SLO。A 的裸吞吐更高，B 的 goodput 却是 81 req/s，比 A 的 60 req/s 更好。A 的 attainment 为 60%，B 为 90%。若再有人说 B 的 attainment 是 A 的 1.5 倍，这并不意味着 B 的延迟缩短了 1.5 倍，也不意味着 GPU 成本自动下降了相同比例。

Agentic 服务还要区分 一次模型调用 TTFT 与 用户任务首次可见响应时间。内部生成的工具参数不一定展示给用户；内部调用已经快速地产生了 token，用户仍可能在等待最终答案。因此最重要的计时器要从用户的根任务到达时开始，而不是在每轮模型调用时重新归零。

3. Agentic AI 的额外优化空间在哪里

3.1 一个用户任务对应多次计算与等待

考虑一个通用任务：“比较几家供应商的报价，并解释差异。”系统可能先用模型决定检索计划，随后并行查询几个数据源，再把工具结果交给模型形成答案。用户只发出一次请求，系统却创建了多个子任务。我们把用户任务称为 root request，把具体模型或工具调用称为节点，节点之间的“必须先完成谁”称为依赖边。

把已经展开的依赖画出来，可以得到一个有向无环图（DAG）。真实 Agent 可能循环重试，系统应把每次实际发生的循环展开成新节点，而不是假设一开始就知道全部 DAG。只有依赖已经满足的节点才是 runnable；等待工具的节点不是可调度 GPU 工作，不能为了“优先级高”就让它占据执行槽。

3.2 多次排队的成本会叠加

若一个任务串行调用模型三次，每次都被当作新请求排队，那么根任务的等待时间是三次排队之和。假设每次排队 60ms，即使计算本身没有变，光排队就贡献 180ms。若保留 lineage 后能在不过度伤害其他任务的前提下把每次等待降到 20ms，就节约了 120ms。这个教学例子说明：优化不一定要让矩阵乘法更快，也可以减少被重复支付的排队成本。

但“保留根任务年龄”不意味着老任务永远优先。一个早到却仍要执行很多轮的任务，可能持续阻塞刚到、只需几十毫秒即可完成的任务。这里存在平均完成时间与公平性的真实冲突，需要剩余工作估计、deadline 与配额共同决策，而不是把 FCFS 的时间戳换一下就结束。

教学例子：调度改变完成时间，不一定改变计算总量

先忽略 batch，假设一个简化执行器在 t=0 同时收到 A、B、C，执行时间分别为 100、10、10ms。如果顺序是 A→B→C，三个任务在 100、110、120ms 完成，平均完成时间为 110ms。改成 B→C→A，完成时间变成 10、20、120ms，平均值降为 50ms。

两种顺序的总计算量都是 120ms，最后一个任务也都在 120ms 结束；收益来自让更多短任务更早完成，而不是 GPU 算得更快。但若短任务永远不断到来，始终选择最短任务会让 A 很久得不到服务。这就是为什么“预计剩余工作少者优先”必须配上 aging、配额或 deadline，不能孤立使用。真实 GPU 还允许 batching，并存在不同资源瓶颈，因此这个串行例子只解释排序动机，不是完整的 GPU 性能模型。

3.3 内部 token 不可见，但并非没有时限

最终答案的流式 token 直接影响用户体验；内部模型调用的 token 则可能是供工具读取的 JSON。后者的逐 token 间隔也许不必与最终答案同样平滑，但完整 JSON 越晚结束，工具就越晚启动，根任务仍会变慢。因此“内部 TBT 可以放松”的正确含义是允许更多短暂的调度弹性，不是允许内部推理无限期被饿死。

阶段目标应该由产品契约和工作流定义。某些服务会把推理过程直接流式展示给用户；某些工具必须在严格期限内被调用。调度器不能只凭“这是 reasoning”标签就推断它不重要。它应同时看节点 deadline 和对后续关键路径的影响。

3.4 有些时间根本不是 GPU 调度能够消除的

若任务 70% 的端到端时间花在外部工具等待，GPU 部分只占 30%，即使把 GPU 部分缩短一半，总耗时也只是原来的 0.70 + 0.30 / 2 = 0.85，也就是约 1.18 倍加速。即使 GPU 时间趋近于零，极限也只有 1 / 0.70 ≈ 1.43 倍。这是 Amdahl 定律的直接应用。

所以 Agentic 工作负载有结构性优化机会，但不能先验声称它一定比普通聊天获得更高收益。收益大小取决于排队占比、工具占比、请求异质性、可重用上下文和 GPU 压力；如果瓶颈在外部 API，必须同时优化工具路径。

4. 用三篇论文解释这些机会，而不是拼接三个宣传数字

4.1 AdaGen：相同负载总量不代表相同执行顺序

AdaGen 的核心观察是：两个实例即使承担相同 token 数，prefill 和 decode 出现在不同 iteration 中，TTFT 仍会不同。它因此预测输出长度、模拟实例调度器，然后进行长度感知路由、分布感知重分配和选择性阶段拆分。论文在其测试条件下报告，相比增强的 Llumnix 基线，TTFT SLO attainment 最高约为 2 倍。这个结果支持“布局值得优化”，而不是证明任意 Agent 工作流都能得到同等收益。[A，§4–5]

迁移到 Agent 场景时，可以保留“预测—模拟—纠偏”方法，把预测对象从单次输出长度扩展到后续阶段；但剩余轮数、工具时延和任务质量是新增问题，不能当作 AdaGen 已经验证过的能力。

4.2 USHER：一个 GPU 的资源不是一根刻度条

USHER 研究多模型共置。它分别估计计算与内存相关需求，选择 batch、replica 和 GPU 放置，并进一步处理 cache 干扰。传统做法可能在显存尚有余量时继续放入模型，却忘记两个模型已经在争抢同一内存通道。也可能计算单元仍有余量，但新模型根本装不进显存。[U，§2–4]

Agent 工作流包含不同模型或阶段时，这个视角提醒我们检查资源互补性。不过 USHER 的计算/内存资源估计是其系统中的特定模型，不能把论文的某个 memory-utilization 数字直接当作现代 LLM 的空闲 KV 字节数。显存容量、带宽、cache 竞争必须拆开处理。

4.3 AdaInf：尽快完成过时模型的结果，也可能不是有效工作

AdaInf 关注边缘多模型应用。输入分布发生变化后，推理模型可能需要增量重训练；训练消耗 GPU，但不训练会降低准确率。它将数据漂移影响、应用 DAG、推理时限、训练预算与内存搬运联合考虑。[I，§2–4]

这对 Agent 服务的启示是评价函数中必须包含任务质量，而不是不加限制地减少 reasoning 或换用小模型来制造“性能提升”。但质量感知的模型路由、检索更新或推理预算控制是这里的工程类比，不等价于 AdaInf 已为 LLM 提供了这些功能。

5. 用一个显存算例理解为什么需要预测

5.1 权重常驻，KV-cache 随请求增长

模型权重是执行模型所需的参数；KV-cache 保存注意力层已经计算出的 key 和 value，避免生成下一个 token 时重新计算整个历史。它不是最终答案缓存，也不是工具输出数据库。已有 KV 只有在模型版本、token 前缀、位置编码及相关执行配置兼容时才能直接复用，语义相近的两段话不代表 KV 相同。

对一个常见、未考虑额外压缩的注意力实现，可以用下面的近似估算整个模型的每 token KV 字节数：

KV bytes/token = 2 × 层数 × KV heads 数 × head dimension × 每元素字节数

式子最前面的 2 对应 key 与 value。这里使用的是 KV heads 而不是 query heads；采用 grouped-query attention 时二者可以不同。张量并行时，每个设备承担多少还取决于 KV 分片与复制方式，不能无条件地把总量除以 GPU 数量。

教学例子：看似很小的 KV 如何填满 GPU

假设 32 层、8 个 KV heads、head dimension 为 128，KV 使用每元素 2 字节，则每 token 为 2 × 32 × 8 × 128 × 2 = 131,072 字节，即 128KiB。一个包含 8,192 个已缓存 token 的序列占约 1GiB KV；64 个这样的序列仅 KV 就需要约 64GiB。

再假设模型有 80 亿参数，权重每参数 2 字节，原始权重约 16GB，也就是约 14.9GiB。两项之和已接近 78.9GiB，还没有加 attention workspace、执行图、内存分配碎片和运行时保留空间。因此即使设备标称 80GB，也不能承诺一定放下。这个例子只用于解释量级，不是任何指定模型的实测配置。

5.2 P90 预测不是防 OOM 的证明

若按预测的 P90 输出长度预留显存，仍有一部分请求会比预测长；当许多请求同时运行时，单请求的覆盖率也不能直接当作整个 batch 不溢出的概率。因此预测用于提高分配效率，真正的安全边界必须由执行引擎对可用 KV blocks 做原子检查，并在没有空间时停止接纳、换出或在安全点抢占，而不是让模型继续写入不存在的缓存。

这正是“软性能预测”与“硬资源约束”的区别。调度器可以依据预测冒一定 SLO 风险，却不能因为预测看起来乐观而绕过物理容量检查。

6. Scheduler 需要什么信息，以及从哪里获得

6.1 编排层提供任务语义，不要求上传全部原始文本

最低限度需要根任务 ID、当前节点 ID、依赖完成状态、任务最初到达时间、阶段类型、最终 deadline 和租户配额。根任务 ID 让系统知道“这是同一用户任务的继续”；依赖状态避免执行尚未就绪的节点；deadline 决定它还有多少时间可以等待。这些是编排层知道、GPU 引擎通常不知道的信息。

不必为了调度把整份用户文档复制到控制面。很多预测可用 token 数、工作流类别、已发生轮数和匿名化工具类别完成；prefix key 应使用与租户隔离、模型版本及缓存协议一致的标识。会话与缓存元数据也要遵循过期和访问控制，不能因追求缓存命中而跨租户泄漏上下文。

6.2 推理引擎提供执行状态，监控面提供硬件状态

引擎应报告实际排队节点、剩余 prefill token、decode 已生成 token、KV block 占用、批次 token budget、模型与 adapter 的驻留情况，以及最近 step 的执行时间。GPU 监控则补充显存容量、计算活动、内存带宽和链路状态。两类信息必须结合：监控图上的 GPU utilization 不能告诉你队首是否有一个即将错过 deadline 的请求，而单看队列又不知道正在发生的网络拥塞。

遥测也有时效性。如果控制面每秒更新一次，而一个 GPU step 只持续十几毫秒，就不能把这份快照当作每一步都精确的真相。因此容量接纳由本地引擎最后确认，远端控制器只提供建议或带版本的 reservation；建议过期时重新评估。

一组可用于最小实现的调度字段
对象最小字段失去这些字段会怎样
根任务ID、到达时间、deadline、租户配额无法计算端到端年龄，也无法限制某个任务持续占用 GPU。
当前节点依赖、模型、阶段、输入长度、输出上限、可见性不知道能否运行、需要哪种模型、该保护什么时限。
运行实例队列、KV blocks、驻留模型、当前批次、step 时延只能依据粗糙请求数量路由。
预测模型耗时和长度分布、置信度、近期误差无法比较不同放置的未来影响，也无法发现预测失效。
互联拓扑、有效带宽、进行中迁移、目标容量可能把排队问题换成更严重的传输问题。

6.3 性能模型预测的是“在这里运行”，不是“独占时多快”

离线 profile 至少应覆盖模型、精度、GPU 类型、batch 形状、prompt 长度、上下文长度和并行配置。运行时再用观测更新残差。例如相同 prefill chunk 与不同数量 decode 共批，会形成不同的执行时间。只存一条“这个模型推理 50ms”的平均值，无法支持正确的 batch 决策。

输出长度、工具等待和后续轮数也应保留分布或分位数。P50 是中位数，不是期望值；如果要优化期望完成时间，应该估计期望或对样本分布积分，而不是把 P50 直接代入后称为“期望优化”。更重要的是，原始特征不等于因果保证，工作流改变或工具失败后都要重新校准。

7. 先定义不可违反的约束，再比较哪个方案更好

把延迟、成本、质量、公平性写成一个加权和看起来很完整，但如果单位没归一化，把 100ms 与 0.01 美元直接相加没有意义；如果权重随意设置，高收益任务甚至可能“买掉”物理容量或既定的服务契约。因此一个更容易实现和解释的教学方案是分层决策。

第一层先检查模型兼容性、权限、依赖、显存、拓扑等可行性。第二层在可行方案中优先保护已经接纳的 deadline 与租户最低服务。第三层才比较预计完成的有效根任务数、等待时间、局部性与增量成本。SLO 是统计目标时，可以约定明确的风险预算，但必须区分“预测可满足”与“确定保证”。

slack(r) = deadline(r) − 当前时间 − 预计剩余关键路径耗时

slack 表示当前任务还有多少可被排队消耗的时间。若任务最终期限在 1 秒后，而预计剩余关键路径需要 800ms，slack 只有 200ms。关键路径要包含串行模型调用、必要的工具等待和数据搬运；并行分支等待汇合时取较慢分支的完成时间，而不是把所有分支耗时简单求和。未知分支则使用条件预测或明确的保守预算。

slack 已经为负时，调度器不能把它夹成一个极小正数，然后永远赋予最高优先级。一个不可挽救的任务如果无限抢占，会让原本可完成的任务一起违约。此时应进入显式过载处理：允许的降级、取消无用分支、拒绝新任务或通知应用，而不是隐藏失败。

公平性也应在 admission 时有容量预算。仅在最后“有空再照顾长期等待者”不是防饥饿算法，因为高负载下可能永远没有空位。租户配额、服务债务和最大等待门槛需要在候选选择中生效，不能被吞吐优化无限覆盖。

8. 为什么要分成三个控制尺度

慢速控制器决定模型放在哪类 GPU 上、需要多少 replica、并行组如何组建、哪些 adapter 预热。模型加载和并行组重建可能很昂贵，所以这类决策不应每个 token 都执行。它与 USHER 的配置和 placement 优化最接近，但现代 LLM 还要加入动态 KV 和通信拓扑。

中速控制器决定新模型调用路由到哪个实例，必要时为已有请求评估迁移或 prefill/decode 分离。它需要 AdaGen 式的队列与未来布局视角，但只对少量候选做有限窗口模拟，不能把复杂搜索放在每次输出 token 的关键路径上。

快速控制器位于推理引擎，每个 step 决定实际选哪些序列、每个 prefill 分配多少 token、能否接纳新 KV blocks。它必须尊重中速控制器的策略，也必须对实时容量有最终裁决权。AdaInf 的慢速质量评估与快速资源调度说明了分层的价值，但三个控制器的具体频率应按系统开销测量，不应照搬另一篇论文的固定时间参数。

9. 集群级算法：从一个调用到达到选定 GPU

下面给出的是一个有限候选、滚动规划、局部提交的工程算法，不是已证明全局最优的调度器。它的特点是每步都明确输入、决策和输出，并允许预测错误后重新规划。

9.1 收到事件，恢复根任务与可执行状态

事件可能是新用户任务、工具返回、模型调用完成或超时。控制器先更新对应根任务图，标记已经完成的依赖，再提取新就绪节点。工具返回时只恢复相应节点，不重置根任务到达时间；如果根任务已经取消，应丢弃过期回调，并避免继续消耗 GPU。

9.2 估计剩余工作，并计算当前预算

从输入长度、模型和历史信息估计该节点的 prefill/decode 时间与 KV 增量，再结合已知后续节点估计根任务剩余关键路径。输出不是一句“它很紧急”，而是具体的 deadline、slack、预测区间和置信度。置信度低时增加延迟裕量，但仍由物理 KV 检查控制内存安全。

9.3 筛选少量候选实例

先排除不支持该模型或版本、隔离策略不允许、显存无法接纳、并行拓扑不兼容的实例。剩下的候选中，可以分别选一个局部性最佳实例、一个预计完成时间最短实例和一个低成本实例。这样不必在每次调用时遍历所有 GPU 的所有 batch 组合。

“模型未加载”不一定永远排除：如果请求时限允许，可把加载成本计入慢路径扩容。但对于只有几十毫秒 slack 的交互调用，现场加载大模型通常不是一个现实候选。筛选规则需要明确区分在线立即可用与未来可能可用。

9.4 在候选上模拟插入后的影响

模拟的不只是新节点自己多久完成，还包括它挤占了谁的 prefill、拖慢了谁的 decode、引入多少 KV 增长以及是否触发换出。比较插入前后的预测 deadline miss 与有效完成数，才知道这是提升整体服务还是让一个新任务靠伤害十个旧任务获得快速响应。

仿真窗口不可能无限长，因此窗口之外的任务使用终端成本近似；候选数量、窗口长度与布局更新频率都应该有明确上限。设每批待分配 W 个节点、每节点 K 个候选、每候选评估 B 个配置、每次模拟 H 步，最外层工作量随 W×K×B×H 增长，单步内部的队列操作还会增加成本。这说明剪枝不是可有可无，而是在线实现的前提。

9.5 按一致的次序选择，并原子预留

先拒绝违反硬约束的动作，再比较预计新增违约数量；相同风险下再比较根任务有效完成、增量 GPU 时间和通信成本。确定目标后，必须向实例提交带版本号的 reservation，并原子占用对应资源。如果多个控制器同时选中同一块空闲显存，没有这一步就会产生“每个决策单独都可行，合起来却溢出”的竞争。

提交失败就刷新状态重新选，而不是假装路由成功。已经接纳的任务则进入实例队列，后续由快速调度器选择真正的执行 step。路由到实例与立刻在 GPU 执行不是同一个动作。

10. 实例级算法：决定下一步真正执行哪些 token

10.1 先决定谁需要服务，再决定能够加入多大 chunk

快速路径首先保护已经接纳、下一 token deadline 最早的 decode 序列，然后在满足这些时限的前提下插入 prefill 或其他序列。这里的选择单位是序列或 prefill chunk，不是把同一序列未来多个自回归 token 当作彼此独立的作业任意调换。通常一次普通 decode step 为一个活跃序列生成一个新 token；推测解码等机制有额外规则，不在此教学算法中假设。

针对 prefill，要做的是选择 chunk 大小，并估计加入后整个 batch 的时长。即使 batch token 数不超限，一个过长 prefill 也会推迟所有 decode 输出。USHER 提醒我们资源约束有多维，AdaGen 提醒我们时间布局有影响；二者结合后的 admission 条件应同时包含容量与时间，而不是只检查 num_tokens < max_tokens。

schedule_step(snapshot):
    ready = nodes_with_satisfied_dependencies(snapshot)
    obligations = accepted_token_deadlines_and_fair_shares(ready)

    batch = reserve_earliest_deadline_decode(obligations)
    if not physically_safe(batch):
        surface_capacity_failure_and_apply_supported_recovery()
        return

    for candidate in ranked_ready_prefills_and_decodes(ready):
        for chunk in bounded_candidate_chunk_sizes(candidate):
            proposal = batch + chunk
            if not fits_tokens_sequences_and_KV_blocks(proposal):
                continue
            finish = now + predict_step_time(proposal) + uncertainty_margin
            if breaks_existing_deadlines_or_fair_share(proposal, finish):
                continue
            keep_best_feasible_proposal()
        batch = chosen_proposal_or_unchanged_batch

    atomically_reserve_blocks_and_dispatch(batch)
    record_actual_time_and_update_prediction_error()

长期等待任务的公平份额属于 obligations，不是把 batch 填满后才临时追加。如果在当前负载下，严格时限和最低公平份额不能同时满足，问题已经是容量不足，必须减少接纳或执行明确的降级。没有一种排序公式能在有限 GPU 上同时满足无限需求。

10.2 把“动态优先级”变成明确的比较规则

为了避免把最关键的排序留在一个黑盒中，可以为这套教学实现规定确定性的顺序。先把即将到期、已经接纳的 token 服务以及本窗口应兑现的公平份额列为 obligation；在能够联合满足它们的前提下按最早 deadline 排入。普通候选再按下面的元组升序比较，不把不同单位的量强行相加：

普通候选排序键 = (紧迫等级，根任务 slack，租户虚拟服务时间，预计剩余 GPU 工作量，入队序号)

紧迫等级可以明确分成“若跳过下一步就有时限风险”和“暂有余量”两类，边界由预测 step 时间和误差裕量计算，而不是随意写一个高优先级标签。根任务 slack 使用相同的时间单位。虚拟服务时间则把租户已消耗的服务量除以其权重，值小者表示相对少获得服务；这个量的计费方法必须固定，例如按实际分摊的 GPU 时间更新。入队序号用于最终打破平局，使回放可重复。

这个排序仍是启发式，不是证明最优的定理。它的作用是让实现和实验可解释：某个候选为什么先于另一个，有一个可记录的比较理由。即使候选排第一，也必须通过 batch 耗时和真实容量检查；排在后面的资源互补候选仍可能在前者暂时不可放入时得到机会。公平性保证来自 admission 时预留的可实现份额，而不是声称元组中的一个字段自然就能消除饥饿。

11. 手算一次调度：为什么剩余 token budget 不代表可以继续塞

教学条件：现在是 100ms。GPU 上 A 的上一 token 在 96ms 产生，允许间隔 20ms，所以下一 token 必须不晚于 116ms；C 的上一 token 在 98ms，允许间隔 25ms，下一 deadline 是 123ms。另有一个等待 prefill 的节点 P，以及一个仍在合理等待预算内的内部 decode R。假设本例所有候选都通过 KV 容量检查，token budget 为 128。

为了便于手算，假定校准后的批次耗时模型为 L = 6 + 0.12p + 0.5d 毫秒，其中 p 是该批 prefill token 数，d 是 decode 序列数，并额外保留 2ms 误差裕量。真实系统必须测量性能曲线；这里的线性关系只服务于这个例子。

最后一个候选并不是“因为 R 不重要所以随便放进去”，而是因为它带来的增量耗时仍落在已有响应的安全预算内。反过来，64-token prefill 即使 token budget 完全够用，也不该为了填满 GPU 而强行加入。这个例子展示了 token 数约束、KV 容量约束、单步时限约束是三件不同的事。

如果最后实际 step 耗时为 15ms 而不是 11.34ms，说明预测偏乐观；本次 A 的 token 在 115ms 仍可能及时，但余量已非常小。下一步应更新残差、减少 prefill chunk 或增加裕量，而不是继续把旧模型当真。每次实际输出后，还要根据新的 token 时间重新计算下一 deadline。

12. 把 workload 放到哪块 GPU：局部性有时比空闲更重要

12.1 一个路由例子

假设 G0 已缓存兼容的 prompt prefix，预计排队 85ms、剩余 prefill 30ms；G1 较空，预计排队只有 10ms，但无缓存，需要 120ms prefill。暂时假设后续 decode 条件相同，G0 的启动路径为 115ms，G1 为 130ms。只按队列最短路由会选 G1，却可能更慢。

若 G0 的排队涨到 200ms，同一比较又变成 230ms 对 130ms，G1 更好。因此 cache locality 是成本项，不应该是绝对绑定规则。调度器需要比较实际避免的计算量，而不是只看到“有缓存”就固定留在原实例。

vLLM 的 Automatic Prefix Caching 文档明确区分了收益阶段：相同前缀可以避免重复 prefill，但不会自动跳过新答案的 decode。对于几乎没有相同前缀、或者主要时间都花在生成长输出上的负载，不能指望 prefix caching 单独解决全部性能问题。[R2]

12.2 迁移的不是一个轻量 request ID

一个正在 decode 的请求要换实例，通常需要传递可恢复的执行状态与有效 KV-cache。迁移成本取决于历史上下文和已经生成的内容，而非仅取决于最后几个输出 token。目标实例还必须有兼容模型与足够显存。KV 转换、分片拓扑、同步和网络竞争都可能增加代价。

迁移时间近似 = 有效传输字节 / 实测有效带宽 + 同步与排队 + 必要的布局转换

例如迁移 2GiB KV，有效带宽为 20GiB/s，单纯传输就需要 100ms。如果迁移只减少 60ms 排队，在没有可重叠传输的假设下就不值得；若可减少 300ms，则有进一步评估的价值。不能用硬件标称带宽代替有效带宽，更不能把 GiB/s 与 Gb/s 混用。

AdaGen 会考虑 KV 迁移完成前 decode 不能开始的约束：源实例 prefill 完成后，还要等目标具备全部必要状态。迁移应比较源、目标及共享链路上其他请求的净影响，并设置次数与冷却限制，以免请求在多个 GPU 之间反复移动。[A，§4]

12.3 工具等待时保留还是释放缓存

某个 root request 进入工具等待后，通常不应保留 GPU 计算槽，但 KV 是否保留需要单独决定。工具很快返回且前缀高度可重用时，保留可避免重新 prefill；工具预计要等待几秒而显存紧张时，保留大量缓存可能让其他请求无法接纳。

可以比较“未来复用概率 × 重算代价”与“驻留期间占用显存的机会成本”，再在保留、引擎支持的换出或丢弃重算之间选择。共享 prefix 的引用计数、租户隔离和重新执行的正确性必须保留；不能为了释放空间直接删掉仍被运行序列引用的 KV blocks。GPU 上运行的检索或 embedding 工具还需要计入实际资源，不能把所有工具都当成零 GPU 成本的外部等待。

13. 为什么预测、过载与公平性必须一起设计

未来输出长度和轮数不可能总是预测正确。对熟悉工作流的预测可能很准，遇到失败重试、新工具或新的模型版本却突然失效。这种情况下，一个稳健调度器应该缩小依赖预测的决策范围：少做昂贵迁移、提高安全裕量、采用已知 deadline 与已积累 service time，而不是依旧执行高风险的远期计划。

剩余轮数也不是剩余计算量。更合适的量是对未来每个可能阶段的输入长度、输出长度、模型和工具等待进行条件估计，得到剩余工作分布；信息不足时，把已完成服务量和根任务年龄作为公平性补充。不能给“预计只剩一轮”的任务无限优先，因为最后一轮可能恰好是最贵的一轮。

服务债务可以按某个租户在一段窗口内应得但未获得的服务累计。不过它不应在任务尚未 runnable、等待外部工具时无条件增加，否则长时间工具阻塞后会回来抢占大量资源。根任务年龄用于评价用户等待，服务债务用于评价可执行期间的资源公平，二者含义不同。

过载时应该在接纳前表达容量不足。若应用允许改变模型或减少生成预算，要同时检查质量和产品授权；若不允许，就只能延迟、限流或拒绝，而不是悄悄把严格任务改成宽松任务。已经进入不可完成状态的节点需要显式告警或取消无用计算，防止“GPU 一直很忙，用户一直失败”。

14. AdaInf 的质量视角应该如何借鉴

一个容易误导的优化是让所有请求都使用更小模型或更少推理 token，然后报告每秒完成数量增加。如果任务成功率同时下降，这可能只是更快地产生错误结果。AdaInf 的价值在于把质量维护所需工作纳入资源预算：推理速度与模型准确率不是互不相关的两个产品指标。[I，§3–5]

对于 Agent 应用，可以在应用层定义固定质量门槛，例如可验证的工具结果一致性、任务完成率或有标签集合上的准确率，并在满足门槛的配置间比较成本。在线任务通常没有立即可得的正确答案，因此代理指标需要校准，不能把模型自报“有信心”当作任务正确的证明。

检索索引更新、adapter 更新或评估任务会与在线模型争抢资源，适合放在慢控制环中管理。这里借鉴的是“服务与质量维护联合预算”的思想，不是照搬 AdaInf 的早退网络结构。普通语言模型并不天然支持任意层 early exit，换模型、减少推理预算和结构性早退是不同技术，必须分别验证。

15. 怎样证明优化真的有效，而不是挑一个漂亮指标

15.1 回放必须保留因果顺序

评估 Agent trace 时，不能把真实运行中所有子请求的时间戳固定后独立重放。调度策略让前一轮更早完成，会改变下一次工具调用和下一轮模型请求的到达时刻；固定子请求到达时间等于剥离了调度对工作流的反馈，可能高估或低估收益。更合理的回放保留用户根请求的外部到达过程，并根据依赖完成、工具耗时样本和分支规则动态释放后续节点。

比较策略时要保持模型、输入、输出工作量和质量要求一致。模拟器需要先用真实 GPU 结果校准；扩大到数百实例的模拟实验能说明算法开销和趋势，却不能直接证明真实网络拥塞条件下也有同样收益。

15.2 应报告什么

核心结果应包括根任务端到端时延的 P50/P95/P99、最终响应 TTFT、流式 gap 分布、满足质量与时限的任务 goodput，以及每个成功任务消耗的 GPU-seconds。把内部调用单独统计可以帮助定位原因，但不能替代根任务体验。

资源指标用于解释机制：KV 高水位、缓存命中、SM 活动、内存带宽、迁移字节和调度开销。如果仅利用率变高而 goodput 没变，系统可能只是在执行更多非关键工作。还应报告按租户、长短上下文、工具长尾和预测误差分桶的结果，避免平均数掩盖一类请求被系统性牺牲。

15.3 如何设计有说服力的对照

首先与现有引擎的真实默认策略比较，再依次加入 lineage、deadline-aware batch、局部性路由、布局模拟和迁移；每增加一个模块都要单独看增量收益与开销。对预测器还应比较真实预测、无预测和“知道未来真值”的 oracle 上界。oracle 只用于估计理论空间，不能混在真实在线结果里。

压力测试应包括长输出、异常工具延迟、相关流量突发、缓存失效、链路变慢与节点故障。若某项收益只在完美长度预测、无限带宽且工具无长尾时出现，它更接近算法理想化结果，而不是可上线的承诺。

16. 面向初学者的实现顺序

第一阶段不要急于写复杂优化器。先在编排层打通 root request 与模型调用 lineage，区分工具等待和 GPU 排队，并建立能正确计算端到端时间的仪表。没有这一层，无法判断改善了哪段路径，更无法验证是否把问题从一个阶段转移到另一个阶段。

第二阶段实现一个有限功能的回放器和实例策略：保留原有 continuous batching，只改变候选序列的次序和 prefill chunk 大小，加入 deadline 与容量检查。用本文的手算例子作为小规模正确性测试，再逐步加入真实 profile。先让规则解释得清楚，再引入学习预测。

第三阶段加入集群路由。最初只比较几类可解释成本：预计队列时间、缺失 prefix 计算、所需 KV 余量和实际互联成本。观察影子调度建议与真实运行结果，确认预测能区分候选后再正式启用。

第四阶段才考虑已有请求迁移、模型重放置和质量维护联合预算。这些动作有较大的系统副作用，需要状态转移协议、重复请求去重、迁移失败恢复、版本一致性与回滚。三篇论文的启发可以组合，但不能替代生产系统需要的工程协议。

17. 用几个问题检查是否真正理解

两个 GPU 的利用率一样，为什么路由结果仍然不同？

利用率不包含队列中阶段的排列、未来 KV 增长、缓存命中和 deadline。一个 GPU 可能刚开始长 prefill，另一个即将结束一批 decode；当前百分比相同，接纳新请求后的完成时间仍不同。AdaGen 优化的正是粗粒度负载数字看不到的布局差异。

内部推理不展示给用户，是否可以永远排在最终答案后面？

不可以。内部调用完成后才会启动工具或进入最终响应，长期延后会让根任务无法完成。可以放宽局部流式平滑要求，但仍需要根任务 deadline、关键路径预算和公平服务份额。

P90 长度预测能否作为显存不会溢出的保证？

不能。预测存在超出分位数的尾部，还可能有相关错误。它适合做预留和风险控制，物理安全必须由引擎对可用 KV blocks、workspace 和真实分配做最终检查。

为什么资源互补的两个阶段并不一定适合共批？

互补只是潜在容量收益。加入 prefill 后可能让 batch 的总执行时间超过已有 decode 的 deadline，或者仍然争用同一 L2 cache 和互联链路。必须同时评估多维资源与时间约束。

三篇论文的最大收益能否相乘，估计组合系统收益？

不能。它们使用不同模型、硬件、基线和目标，解决的问题也有重叠。组合收益应通过统一实现和同一工作负载上的消融实验测量，不能把 attainment、成本与准确率的改善倍率混算。
