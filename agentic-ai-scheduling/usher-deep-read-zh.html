USHER：为什么 GPU 放得下多个模型，却不一定服务得好？

这是一篇从基础概念开始的中文教程，而不是论文摘要的条目扩写。我们要回答一个实际问题：一张 GPU 还有空闲资源时，能不能把另一个模型搬进来，同时让用户等待得更短、让服务成本更低？USHER 的回答不是简单的“可以”，而是先认识资源，再联合选择批大小、副本数和放置位置，最后处理共享缓存带来的干扰。

原论文：Sudipta Saha Shubha、Haiying Shen、Anand Iyer，Usher: Holistic Interference Avoidance for Resource Optimized ML Inference，OSDI 2024，正文第 947–960 页。USENIX 官方页面 · 官方完整 PDF · 作者公开代码。

阅读约定：“论文报告”指原文结果；“教学示例”中的数字为本文构造，不是论文测量；“工程延伸”是面向现代部署的分析，不冒充原算法。本页引用同时给出论文节号和印刷页码；PDF 多一页封面，例如印刷第 952 页对应 PDF 第 7 页。数学用普通文字及上下标表达，无需脚本或公式 CDN。

1. 先拆开 GPU 的几种“利用率”

可以把 GPU 想成一座工厂，但不要把所有资源都叫“工厂繁忙程度”。SM，即流式多处理器，是执行线程块和计算指令的主要单元；HBM 是 GPU 外部的高带宽显存；L2 是位于芯片上的共享缓存层。工人有多少、仓库装了多少、每秒能搬多少货、工作台上放了什么，是四个不同的问题。这个区分不是术语洁癖，而是决定共置是否合法、是否变慢的基础。

1.1 SM、occupancy 与 FLOPS 不是同一把尺

一个 CUDA kernel 是在 GPU 上启动的一段计算程序。线程以 warp 为单位被调度，一个 SM 可以同时容纳多个 warp。achieved_occupancy 的定义，是活动周期内平均活跃 warp 数与该 SM 支持的最大 warp 数之比。它描述“有多少 warp 驻留并处于活跃统计范围”，不是“峰值算力已经兑现了多少”。warp 可能正在等内存，也可能受到指令依赖、寄存器、共享内存或执行流水线限制。高 occupancy 有时能掩盖访存延迟，却既不是高性能的充分条件，也不是所有高效 kernel 的必要条件。

FLOPs 通常表示完成一项计算需要的浮点运算次数；FLOPS 表示每秒完成的浮点运算次数。假设一个任务需要 1012 次浮点运算，运行 0.1 秒，实际吞吐就是 1013 FLOPS；这仍然不能推出它占用了多少 SM，或者 Tensor Core 是否高效。GPU 规格中的峰值还依赖 FP32、FP16、FP8、是否使用稀疏路径等条件。因此，“模型参数多”“FLOPs 多”“occupancy 高”和“计算资源需求高”有关联，却不能互换。

USHER 把计算需求写成 Creq，希望表示模型执行期间计算空间需求的峰值比例；实现节又说使用 achieved_occupancy 测量 kernel 的 Creq。读者应把它理解为论文采用的一种计算压力代理指标，而不是把 occupancy 直接当成可精确切割、可线性相加的 FLOPS 配额。MPS 的活跃线程比例设置也不是吞吐承诺。[P §2，第 948 页][P §4，第 956 页][N1，指标定义]

1.2 HBM 容量、HBM 带宽与 L2 缓存

容量以字节衡量，回答“这一时刻能否装得下”。常驻权重、激活、中间结果、框架工作区、内存池以及生成模型的 KV cache 都需要容量。两个模型各有 12 GB 常驻数据，在 16 GB 显存上通常不能同时完整驻留；它们运行时算得快不快，不会改变这个容量事实。实际检查还需留出分配器碎片和运行时开销，不能只把参数个数乘上数据类型大小。

带宽以 GB/s 或 TB/s 衡量，回答“每秒能传多少数据”。一个只分配 2 GB、却反复扫描这些数据的任务可以接近带宽瓶颈；一个分配 30 GB、只偶尔访问其中少量数据的任务则可能没有多少带宽压力。因而，显存分配量占 80%，不代表带宽使用了 80%；带宽压力很高，也不说明显存容量已经耗尽。

L2 缓存比 HBM 小得多，也更靠近计算单元。命中 L2 可以减少昂贵的 HBM 访问，但缓存内容会被替换。两个模型即使都能装进 HBM，也可能互相挤掉反复使用的权重块，造成更多 cache miss，继而增大 HBM 流量。L2 容量、命中率和缓存带宽仍然是不同指标。“我给两个模型分配了不同的张量地址”并不等于“它们拥有互不干扰的 L2”。

原论文有一个必须保留的口径疑点。§2、§3.2 把 Mreq 描述为显存空间需求，并用权重大小加中间数据峰值解释它；§4 却写用 dram_utilization 测量 kernel 的 Mreq。NVIDIA 的该指标是相对峰值的设备内存活动/吞吐利用等级，历史工具中以 0–10 分级呈现，不是 allocated bytes 或 reserved bytes。不能因为名字里有 memory，就把它当成显存容量百分比，更不能把这一等级直接与权重字节数相加。

因此，本文不会替论文消除这个未充分说明的映射：Mreq 的概念模型、实际回归标签和实验中的 Muti，需要复现者进一步核对。真正部署时，应分别记录显存峰值字节数、HBM 读写吞吐、L2 行为和计算压力，统一量纲后再作决策。“USHER 已独立且严格约束了所有带宽和容量”不是现有描述足以支持的结论。[P §3.2，第 952–953 页][P §4，第 956 页][N1]

2. 批处理、副本、排队与 goodput

服务系统首先收到的是请求，不是已经整理好的 GPU 工作。批处理 batching 把同一模型的多个输入合成一个 batch，共用一次调用、权重读取和较大的矩阵计算。例如单请求运行 4 毫秒，四个请求一起运行 7 毫秒，服务能力从每秒 250 个请求提高到约 571 个请求；但批内每个请求的执行时间从 4 毫秒变成了 7 毫秒，早到的请求还可能等待后来者。这组数字只是解释批处理，不是 USHER 的实验数据。

批越大并非越好。它通常增加激活空间和单批执行时间，虽然每个请求分摊的成本可能下降；遇到内存上限或延迟要求，就不能继续增大。实际库还可能换用另一个 kernel 算法，所以性能曲线并不必然光滑。USHER 的关键观察是：批大小只有一个旋钮，却同时影响至少两个资源维度，很难仅靠它同时填满计算与显存空间。[P §1，第 947 页]

副本 replication 则是启动同一模型的多个服务实例，把请求流分给它们。复制不是把一张大模型自动拆成几块：模型并行才是拆分一次推理的模型状态或计算。论文对小模型把一个“模型”视为完整实例；对 Llama-2 这类大模型，底层 DeepSpeed 先进行模型并行，后文的调度对象可以指其中的分区。把一个分区算作放置对象，并不意味着它独立就能回答完整请求。[P §2，第 949 页]

增加副本能分担排队压力，却也复制常驻权重，增加部署和加载成本。更微妙的是，每个副本收到的请求更少，凑出大 batch 可能更慢。因此，增加副本与减小 batch 往往要一起考虑。USHER 把这种 workload division 与放置联合优化：有时一个模型本来一张卡就能服务，拆成两个小 batch 的副本后，反而更容易填入其他模型留下的空隙，最终整组模型需要的 GPU 更少。这不是免费复制，而是用额外权重副本交换更好的资源组合。[P §2.2，第 949–950 页]

2.1 为什么要优化 goodput，而不是总吞吐

SLO 是服务级别目标。若要求请求在到达后 40 毫秒内完成，那么延迟应从到达开始计时，而不是从 GPU kernel 启动开始计时。教学上可分成：总延迟 = 凑批等待 + 已就绪队列等待 + 执行时间 + 传输及其他开销。前两项并不相同：系统可能尚未忙到排队，却已经因为等待凑批而错过期限。真实产品还常规定 p95 或 p99 延迟，而论文使用给定的逐请求时限来统计是否达标。

吞吐统计完成了多少请求；goodput 只统计其中在 SLO 内完成的请求，单位仍然是 requests/s。一个系统每秒完成 1,000 个请求，其中 300 个超时，goodput 就是每秒 700 个，而不是 1,000，也不是一个没有单位的“70%”。另一系统只完成 900 个但全部按时，其 goodput 更高。比较两者必须统一请求到达率、模型集合和 SLO，否则数字没有可比性。

论文的放置算法用“batch size 除以包含排队等待的预期完成时间”近似估计服务能力，并把模型 goodput 截断到实际 workload，避免给没有到达的请求计分。这里不能把 B / (tbatch + tqueue) 当成任何队列系统的精确通用定律：流水线、持续凑批、多副本聚合及超时筛选都可能改变统计口径。尤其不能只看平均延迟来推断每个请求均满足 SLO。[P §2.1，第 949 页][P §3.3.2、算法 2，第 954–955 页]

3. 共置为什么产生非加性延迟

假设模型 A 独占时需要 10 毫秒，模型 B 独占时需要 12 毫秒。把它们并发放在一张 GPU 上，并不能推断 A 仍是 10 毫秒，也不能说 A 的新延迟一定是 10 + 12 毫秒。完全串行执行时，后到者可能等到前者结束；并发执行时，它们则共享不同层级的资源。实际结果可能接近独占时间，也可能两个都显著变慢，要看资源竞争发生在什么阶段。

最直观的是计算竞争：线程块可能因 SM、寄存器或共享内存资源不足而等待。另一个来源是带宽竞争：两个 kernel 同时读取大张量，各自的有效吞吐会降低。第三个来源是缓存替换：A 使 B 的热数据离开 L2，B 下一次访问必须从 HBM 重新搬运；增加的访存又延长了 kernel，令它与 A 的下一阶段重叠。这是反馈过程，所以共置的资源曲线和时序会改变，而不是两条独占曲线永远按原样相加。

例如两个模型独占时都因为高 L2 命中而只消耗中等 HBM 带宽，共置后却同时变成带宽密集型。以独占平均带宽相加作预测会过于乐观。反过来，若 A 的计算密集阶段恰好覆盖 B 的低计算访存阶段，二者又可能形成互补。两两共置数据也未必足够：第三个模型加入后可能使缓存工作集跨过容量阈值，出现此前不存在的严重退化。

论文用 goodput 比值说明这个风险：在其 §2 的工作负载和基线设置下，GPUlet 中 87% 的模型、AlpaServe 中 100% 的模型，共置 goodput 与独占 goodput 的比值不高于 0.55。这个数字是模型分布的统计，不是“所有 GPU 的性能都下降 45%”，也不是对这些系统所有配置的永久判决。USHER 的启发是优先选资源互补组合，再专门减少缓存竞争；“避免干扰”是设计目标，不是物理隔离的证明。[P §2.1、图 2，第 949 页]

4. 沿原算法走完一次调度

现在把自己放在系统控制器的位置。输入是一组模型、每个模型当前的请求率和 SLO，以及可用 GPU 类型。控制器首先需要回答“模型以某个 batch 在某类 GPU 上运行，预计需要多少资源、多久完成”；这由 GK-Estimator 提供。它不是先把所有可能共置组合都跑一遍，而是重用离线学习到的 kernel 级知识。

接下来，IR-Scheduler 不直接枚举整个集群的所有模型组合，因为搜索空间会爆炸。它先把具有互补潜力的模型划成适中大小的组，再在组内枚举批大小和副本数组合。对每个候选组合执行放置启发式，计算新增 GPU 成本及预期 goodput；最后按固定集群或弹性集群的不同目标选取候选。这里的“最好”是该分组、候选集合和启发式之下的最好，不是数学意义上求得全局最优解。

位置确定以后，OG-Merger 才去检查同 GPU 的模型是否可以合并部分算子图，以便同一份缓存中的权重块服务多个输入。资源互补与权重相似是两种不同的“分组理由”：前者帮助决定谁住在一起，后者帮助已经住在一起的模型共享什么。不能把 IR-Scheduler 的组直接等同于模型架构相似组。

部署后，系统根据变化重新调度。原文把某模型请求率显著变化设为 0.5k requests/s，并展示了相隔约 45–300 秒发生变化的轨迹窗口。这是一套有一定时间尺度的控制回路，不是每个请求或每个 token 都重新搜索。图合并尚未完成时，论文先使用独立模型图处理请求，再切到合并后的图；因此融合准备时间与服务停顿不能简单画等号。[P §3.1、图 9，第 952 页][P §5.2，开销讨论，第 958 页]

5. GK-Estimator：从算子图到内核图

神经网络通常以算子图呈现：节点可能是卷积、矩阵乘法或注意力算子，边表示输入和中间张量依赖。但一个算子在运行时未必只调用一个 GPU kernel；框架和库可能把它实现为一串 kernel。只看“网络有多少层”，会漏掉真正的并发关系和资源峰值。USHER 先离线观察 ONNX 算子对应的 kernel 序列，再将新模型的算子图展开为更细的 kernel graph。

在这个图中，父节点完成后子节点才能取得所需数据，并行分支则可能同时执行。论文先预测各 kernel 的执行时长，据此估计开始时间；开始时间差不超过 τ 的 kernel，被视作可能并发的一组。默认 τ = 0.001 毫秒，即 1 微秒。对每组求资源需求和，再取各组中的最大值，用于近似整次执行的峰值。

这个阈值是一个时序近似，而不是严格的区间相交算法。假设 kernel A 从 0 到 10 微秒，B 从 5 到 7 微秒，它们实际重叠，但起点相差 5 微秒，已大于 1 微秒。严格重建并发还需要完整区间、所有前驱依赖、stream 调度与设备限制。论文 §5.6 在其测试设置中选择了表现最好的 τ，不能因此推断该阈值适用于所有新 GPU、编译器和异步执行框架。[P §3.2、图 10，第 953 页][P §5.6、图 26，第 960 页]

5.1 回归器到底预测什么

原文以显存需求解释方法，明确命名了 Mreq-Regressor 和 Time-Regressor：前者估计 kernel 中间数据需求，后者估计执行时长。二者使用 stacked regression，即组合多个回归模型来减少单一模型偏差；文中列出的组成是 Lasso、Kernel Ridge、Gradient Boosting 和 XGBoost。输入包括 batch size、kernel 参数权重张量大小、输入中间张量大小、浮点运算量和 GPU 类型。

不要把它缩写为“两个 stacked regressors 分别预测计算和显存”，因为这样会漏掉决定并发关系的时间预测器。系统也估计计算需求，公开的 sm_requirement.py 以 regression_sm 求并发组需求之和，memory_requirement.py 中有类似的 regression_mem 调用；但论文对计算预测细节的展开不如显存示例完整。公开文件也依赖外部图变量和回归函数，不能把这些片段误认为已经提供了一键可运行的完整训练、校准和服务流水线。[P §3.2，第 953 页][A，计算需求代码][A，显存需求代码]

按照论文的容量概念模型，可把 Mreq 的字节形式写成：“参数常驻大小 + 最大并发 kernel 组的中间数据需求之和”，再除以对应 GPU 的总容量得到归一化比例。串行链对应逐算子中间峰值，并行分支对应并发求和。这解释了为什么必须知道图结构。不过，真实框架的中间张量可能活得比生产它的 kernel 更久，workspace、分配器保留区和输出缓冲也会占空间；这个近似不自动等于完整的内存存活期分析。前面指出的 dram_utilization 标签口径问题仍然存在，不能靠写出一个容量公式就视为解决。

这种方法节约的是新模型到来后反复实测的成本，而不是免除所有测量。论文说回归训练离线使用已知 ONNX 算子的 kernel，在 V100 上训练约 1.3 小时。换一个后端、算子融合方式、输入形状分布、精度或 GPU 时，kernel 映射与回归分布都可能改变。此外，其特征不包含将来共置的其他模型，因此 GK-Estimator 本身不是“任意共置组合的精确延迟预测器”。它给调度器提供独立需求估计，再由调度策略与融合降低干扰。[P §3.2，第 952–953 页]

6. IR-Scheduler：目标、分组与 best-fit

6.1 固定资源与弹性资源，目标不是同一句话

固定集群中 GPU 数量和类型已经给定，USHER 要最大化总 goodput；超出集群能力的请求不可能凭算法变成免费资源。弹性集群中允许增加 GPU，目标则是在满足全部模型 workload 与 SLO 的前提下，最小化租用成本。后者不是单纯追求 GPU 数最少：两张便宜卡可能比一张昂贵卡省钱，也可能因复制和通信更慢，必须比较具体配置。

用普通数学表达，固定集群目标为 maximize Σm goodputm，受已有 GPU 与资源可行性约束；弹性集群目标为 minimize Σg price(typeg)，并要求 total_goodput = total_workload。每个 GPU 的候选放置要通过论文定义的计算、显存空间检查，配置也要满足模型延迟条件。副本总数不必小于 GPU 总数，因为一张 GPU 可以容纳多个模型副本；将“replicas placed ≤ available GPUs”写成通用约束，恰好抹掉了空间复用。[P §3.1，第 952 页][P §3.3.2，第 954–955 页]

6.2 先分组，是为了缩小联合搜索

调度器先在可考虑的 batch 与 GPU 类型上估计模型需求，形成平均资源画像。随后用论文所称的 k-means 变体构造近似等大的组，其互补性准则是 D = |Σ Creq − Σ Mreq|。这不是普通的“把最相似模型聚在一起”：一个计算需求大、显存需求小的模型，恰好可能应和方向相反的模型成为一组。它关心的是组的需求和是否平衡，而不是两个向量的欧氏距离是否最小。

过程从单模型组开始，两两合并，再把已有组作为元素继续合并；经过 p 轮，组的规模上限按 2p 增长，文中用四模型组举例。分组降低组内搜索的规模，但也限制跨组联合优化，故它是质量与调度开销的折中。此外，平均画像可能掩盖某个具体 batch 或 GPU 类型上的反转，后续放置仍需对具体候选重新估计资源。[P §3.3.1，第 953 页]

6.3 枚举配置，再按互补顺序做放置

组内配置是每个模型的 (BS, RD)，也就是 batch size 与 replication degree。原算法取 BS ∈ {4, 8, 16, 32, 64, 128}，RD = m × clM，其中 m ∈ {1, …, 6}。clM 按最高能力 GPU 类型、受显存与 128 上限限制的最大 batch，以及 workload/SLO，估计满足该模型服务要求的最小副本数。它是论文搜索范围的构造依据，不是对任意异构设备、动态队列和共置环境都成立的解析最小值。

为什么允许副本数超过 clM？因为局部最少副本不一定产生全局最好装箱。候选中增加副本、降低 batch 后，一个模型的需求块可能变小，能够与别的模型互补，降低最终 GPU 成本。固定集群版本还限制单模型候选 RD 不超过集群 GPU 数，并改为选择总 goodput 最大的配置；这仍不等于限制所有模型副本的总和。

对每个配置，算法先用 GK-Estimator 得到各 GPU 类型上的需求，拒绝最高容量设备都无法承载的候选。然后按平均资源比例标记模型：Creq/Mreq ≥ 1.2 为 C-heavy，反向比例 ≥ 1.2 为 M-heavy，其余相对平衡。这一标签属于“模型 + batch + GPU 等执行条件”，不是模型名字的永久属性。更不能把 M-heavy 未加区分地翻译为“必然是 HBM 带宽瓶颈”；这里沿用论文的资源需求口径。

接着把 C-heavy 和 M-heavy 两列分别按 Creq + Mreq 从大到小排列，交替配对形成待放置列表，再插入平衡型模型。先处理大块，是为了避免最后只剩零碎空隙；交替处理两种资源方向，是为了避免先把所有计算型模型堆到一起。

best-fit 的含义也很具体：先找当前模型组已经使用的 GPU；若多张都能承载，就选放入后剩余 C-space + M-space 最少的那一张。若组内放不下，再尝试其他组已有的 GPU；最后才启动能够承载该模型或候选模型对、且费用最低的新 GPU，并把它加入本组 GPU 集合。算法返回本配置的新增费用和总 goodput，外层比较候选，选定计划。它不是“每来一个请求就贪心挑最便宜 GPU”，也不是只检查显存余量。[P §3.3.2、算法 1–2，第 954–955 页]

教学示例一：归一化计算/显存装箱，不等于带宽安全

假设：两张同型 GPU，每张有 16 GB 可用于本例的显存，计算预算归一化为 1。这里 C 是我们假定可加的调度需求，不是直接读出的 occupancy；M 严格表示已包含工作区的显存峰值除以 16 GB。先忽略带宽、L2、动态分配与迁移，且假定每个模型独立满足 SLO。四个实例的需求如下。这个理想化模型只用于理解装箱，不是论文图 7 的复刻。

教学示例二：大 batch 提升执行能力，却降低按时完成量

假设：单副本每秒均匀到达 200 个请求，即每 5 毫秒一个；只发送满 batch；无旧队列、传输开销与抖动；batch 4 执行 6 毫秒，batch 8 执行 10 毫秒；每个请求的到达至完成 SLO 为 40 毫秒。持续到达与执行可并行，下面分别观察一个完整 batch，从第一个请求到达时刻 0 开始。

batch 4 的到达时刻是 0、5、10、15 毫秒，15 毫秒时开始执行，21 毫秒时一起完成。四个请求的延迟分别为 21、16、11、6 毫秒，全部达标。执行能力为 4/0.006 ≈ 667 requests/s，但实际只到达 200 requests/s，因此稳定期 goodput 是 200，不是 667。

batch 8 在 35 毫秒才能收齐，45 毫秒完成。请求延迟依次为 45、40、35、30、25、20、15、10 毫秒，最早的一个超时。尽管执行能力升到 8/0.010 = 800 requests/s，且平均延迟仅 27.5 毫秒，仍有八分之一的请求违反 SLO。在上述严格均匀且忽略边界的假设下，goodput 为 200 × 7/8 = 175 requests/s。平均达标，不能代替逐请求达标。

若把流量均匀拆给两个副本，每个副本只有 100 requests/s，间隔变为 10 毫秒；使用 batch 4 时最早请求需等 30 毫秒凑批，再执行 6 毫秒，总共 36 毫秒。原来的 21 毫秒反而变长了。副本扩展能在过载时缩短就绪队列，却可能在低负载时拉长凑批时间，所以需要 batch timeout、动态批大小以及副本联合选择。这个例子没有突发与已有队列；加入这些因素后，必须看延迟分布，不能直接照用这里的 175 或 200。

8. OG-Merger：复用相同权重，而非混合模型

IR-Scheduler 试图把计算与显存空间分配好，但 L2 缓存不能简单给每个模型都保留完整工作集。论文指出其设置中模型对缓存的需求接近整个缓存，若机械要求各自缓存需求之和不超过一张卡，就几乎不能共置。OG-Merger 换了一个方向：如果两个模型本来就在用相同或极接近的权重块，能否让这些块在 L2 中时连续服务多个输入，而不是反复换入换出？[P §3.1，第 952 页]

8.1 架构相似只是候选条件，权重相似才决定可共享部分

同 GPU 的模型先用 DBSCAN 按算子图的 graph edit distance 聚类。图编辑距离衡量把一个算子图改成另一个需要多少添加、删除或替换操作；DBSCAN 不要求预先指定组数。原文以很小的距离阈值举例，意图找非常接近的结构，不应解读成任意两个 Transformer 都能合并。

同一架构组内，算法取两个模型建立算子二部图。一侧是模型一的算子，另一侧是模型二的算子；只有算子类型相同、预计开始时间相同、权重相似度至少达到 ω 时才连接。默认 ω = 40%，边权为相似度。Hungarian algorithm 选择总边权最大的互不冲突匹配，避免同一算子同时被多次匹配；之后再逐步加入其他模型。这是受候选条件和合并顺序约束的过程，不是自动发现所有全局最优公共计算。

权重相似度也不是“语义接近”或“向量余弦相似”。论文用两倍最大公共权重子矩阵的元素数量，除以两个权重矩阵的元素数量之和；认为两个权重值相同的条件是绝对差不大于 10−7。对模型级统计，再对相关卷积层或注意力层对取平均。这里的 40% 是算子匹配门槛，并不意味着把两个模型 40% 的参数直接取平均。

论文在从 Hugging Face 选择的 1,000 个 CNN 与 1,000 个 Transformer 模型中分别测量：52% 的 CNN 模型对位于 (45%, 65%] 相似度区间，70% 的 Transformer 模型对位于 (55%, 70%]。这些比例依赖公共子矩阵定义、精度、检查点来源和采样集合，不能推广为“随便两个独立训练模型都共享大半权重”。同源基础模型和微调后保留的权重是合理的共享来源；网络结构相同，本身并不保证数值相同。[P §2.4，第 951–952 页][P §3.4.1–3.4.2，第 955 页]

8.2 Super-Operator 怎样保存各自的输出

以两个线性运算 y1 = W1x1、y2 = W2x2 为例。在共享子块已经对齐且完全相等的简化情况下，可把 W1 = Ws + R1、W2 = Ws + R2。把不同输入拼成 [x1, x2]，一次 GEMM 计算 Ws[x1, x2]，再分别加回 R1x1 与 R2x2。它共享的是权重读取和执行组织，各模型仍保留自己的输入、剩余权重及输出。

原算法更具体：用 template matching 提取最大公共子矩阵，构造其余位置为零的共享矩阵；原矩阵中对应区域置零，得到残余矩阵。必要时先对输入、权重做零填充，再拼接输入，创建共享 GEMM 和独立剩余运算，最后进行输出重定位与求和。第一个模型与第二个模型的公共块可能位于不同位置，论文专门讨论了重定位。实现者仍须检查索引、布局与输入维度语义；不能因为有“共享矩阵”这个名字就省略这些操作。

收益主要来自让共同权重在 cache 中被多次利用，而不是把不同输入的矩阵乘法结果直接复用，也不是保证浮点运算数减半。零填充、拼接、拆分、残余运算、重定位和额外 kernel 都有成本。ω 太高会错过共享机会，太低则接纳共享很少的算子，使这些开销压过收益。论文在其设置中选 40%，是性能权衡的结果，不是普遍适用的常数。[P §3.4.3、图 11–12，第 955–956 页][P §5.6，第 960 页]

8.3 数值精度不是可以省略的附注

如果公共值完全相同，代数分解在实数运算下成立，但浮点加法的顺序改变仍可能影响末位；若只是差值不超过 10−7 就视作相同，复用公共值还引入近似。这个绝对阈值与数值尺度、数据类型有关：FP16、FP32、FP8 在不同量级上的可表示间距不同，不能把同一个阈值当成通用误差保证。局部很小的权重扰动经过多层传播后，任务级影响也需要测量。

论文当前实现使用 FP16，并把其他精度及自适应选择留作未来工作；表 2 报告图合并的平均模型准确率变化为 −0.0003%，表 3 给出逐模型结果。这是作者在其数据与任务上的报告，不是逐输出误差上界，更不是对生成模型任意长回答的语义等价证明。不同任务的“accuracy”也未必天然可合并为同一种统计量。量化还会同时改变权重大小、带宽、Tensor Core 路径和相似性，所以不能先在 FP16 下做好资源计划，再认为换 FP8 一定只会更省。[P 表 2–3，第 958–959 页][P §6，第 960 页]

大规模评估把 GPU 数扩到 6,000、请求率扩到每秒 1,500 万，但这是模拟。原文明确说由于成本过高，没有在这些 GPU 上真正运行模型，而是直接从调度决策报告结果。因此它支持“大规模下调度方案的估计收益”，不等于证明 6,000 卡真实运行时的尾延迟、网络拥塞、故障恢复和缓存干扰均已被验证。

10.1 “99.98% 准确率”没有那么简单

§3.2 报告在表 1 的模型、BS = 2 的实验中，计算与显存需求估计准确率为 99.98%；表 4 又给出跨表 1 模型平均的同名准确率，以及 GK-Estimator 耗时 31.6 毫秒、对比 profiling 4.8 小时和 42.7 美元。两处结果应按各自上下文阅读，不能说所有 batch、所有 GPU 和所有未见模型都达到了相同准确率，也不能把 31.6 毫秒理解为系统端到端调度时长。

原文没有充分给出“准确率”的统一数学定义、误差分布、置信区间以及未见算子或未见 GPU 的独立泛化检验。因此不能将其自动解释为每个预测误差都不超过 0.02%，更不能理解成 SLO 违约率仅为 0.02%。profiling 被视为对照真值也不意味着它无测量扰动。复现至少需要明确相对误差如何计算、是否有容量低估的高风险尾部，以及资源标签的量纲。

表 4 将估计阶段的 GPU profiling 成本记为 0，但离线训练已经花费约 1.3 GPU 小时，CPU 推断、图分析和模型维护也不是不存在。准确说法是“摊销既有 kernel 知识后，显著减少新模型逐配置 profiling”，不是“训练与运行完全免费”，也不是将 31.6 毫秒舍入为零后宣称时间减少 100%。[P §3.2，第 953 页][P §5.5、表 4，第 959 页]

10.2 0.51 秒只是决策开销，不是整个切换过程

表 2 分别列出分组 0.1 秒、调度决策 0.51 秒、模型加载 0.63 秒、图合并 2.3 秒。分组主要在模型增删时更新；图合并可在独立模型图先服务时继续准备，所以这些数既不能都忽略，也不应不看是否重叠就直接相加成统一停机时间。正文另给模型迁移加载约 0.69–0.72 秒，与表中口径并不完全一致，表 3 又列出逐模型加载值；使用时应指定引用哪一项。

45–300 秒的变化间隔来自论文展示的工作负载窗口，能说明该控制开销在该窗口内有摊销空间，不是所有生产突发都至少隔 45 秒。短到几十毫秒的 burst、突增的长上下文、模型换入与回滚，都可能需要更快的准入、排队或降级机制。原文也承认突发非常频繁时收益可能降低。

最后，利用率提升只是解释性证据。Cuti、Muti 的测量代理与量纲已在第一节区分，原文某些“提高若干百分比”的叙述也不宜擅自改成百分点。最应优先复核的是统一 SLO 下的真实 goodput、成本分母、输入质量，以及是否真正完成了模型执行。消融说明模块在特定设置中有价值，却不能证明在所有模型组合下都同样有效。[P §5.2，第 957–958 页][P §5.4–5.5，第 959 页]

11. 现代 LLM、动态 KV 与 MIG/MPS 边界

USHER 不是完全没有语言模型：它测试了 BERT、GPT-2 和 Llama-2 13B。但“包含一个生成模型”与“已经解决现代 LLM serving”是两回事。今天的自回归服务通常有 prefill 与 decode 两个阶段；prefill 处理一段输入，decode 逐步产生 token，并持续读写 KV cache。它们的计算/访存比例受序列长度、并发数、注意力实现、GQA、精度和硬件影响。prefill 常更偏计算、低 batch decode 常更偏访存，是可用于提出假设的经验，不是所有条件下的固定分类。

11.1 KV cache 让“显存需求向量”随时间改变

普通 Transformer 的一条序列，若有 L 层、每层 HKV 个 KV head、head 维度为 d、已缓存 token 数为 T、每个元素 b 字节，则未考虑分片和块管理开销的 KV 大小可近似写为：

KV 字节数 ≈ 2 × L × HKV × d × T × b

前面的 2 表示 key 和 value 两份。GQA 会改变 KV head 数，多副本、多序列、分页块、量化和并行分片都会进一步改变实际占用。这是工程容量模型，不是原论文公式。

教学上假设 L = 32、HKV = 8、d = 128、b = 2，则每个 token 需要 131,072 字节，也就是 128 KiB KV；4,096 token 的一条序列约需 512 MiB，十条就是约 5 GiB，尚未包含权重、workspace 与碎片。请求继续生成时，这部分还在增长。因此入场时“刚好放得下”不能保证十秒后仍放得下，调度器需要预测增长、限制并发、保留容量余量，或能够抢占/换出状态。

这意味着现代扩展应把容量、容量增长率、HBM 带宽、L2 压力和互联分别作为维度，再把资源估计与阶段、活跃序列长度分布绑定。continuous batching 每一步都可能换入或移除序列，与论文以有限 BS/RD 候选为中心的模型不同。动态形状、FlashAttention 等融合 kernel 也会改变原有算子到 kernel 的映射，需要重新校准，而不能沿用旧图上的回归值。

11.2 不能把 MIG 与 MPS 的隔离能力混为一谈

论文所用的 MPS 活跃线程比例控制，没有给每个模型独立的 HBM 带宽与 L2 配额。客户端仍可能竞争共享缓存和显存接口；显存分配上限即使存在，也只是容量限制，不是带宽保底。因此，按比例配置 MPS 后仍需真实共置 profile、违约监控和回退。把多个模型融合进一个 CUDA context，也不会自动创造硬件级租户隔离。

但“MIG/MPS 都没有硬带宽隔离”也是不准确的概括。NVIDIA 的 MIG 文档明确区分 GPU Instance（GI）与 Compute Instance（CI）：不同 GI 分配专属的 L2 分区、内存控制器等内存路径，提供对应的容量与带宽资源隔离及 memory QoS；同一 GI 内的多个 CI 则共享该 GI 的内存和部分引擎。在一个 GI 内再通过 MPS 共置，也不能把 GI 层面的隔离误当成各模型间的带宽隔离。

所以，应准确地说：USHER 的 MPS 共置没有硬带宽隔离；MIG 的 GI 边界有更强的硬件内存隔离，但不保证同一 GI 内每个模型获得独立带宽，也不直接保证包含网络与排队的端到端 SLO。MIG 的离散配置与切分限制还可能造成碎片，V100 主实验本身也没有验证 MIG 上的效果。这里对 GI/CI 的解释来自硬件厂商文档，是防止错误迁移的补充，不是原论文新增实验。[P §1，第 948 页][P §4，第 956 页][N2，内存路径隔离][N3，GI/CI 与 MPS]

11.3 可迁移的是方法，不是结果倍数

比较稳妥的迁移路线，是先保留 USHER 的联合优化思想：在请求长度分桶、阶段估计和资源余量下，联合选择 batch、并发度、副本和设备；同时用真实共置执行检查容量、带宽与尾延迟。当 TTFT（首 token 延迟）、TPOT（后续每 token 时间）和整请求时限都重要时，应分别定义是否达标，不能沿用一个请求完成率就掩盖生成卡顿。

OG-Merger 的适用范围则需更谨慎。共享基础权重的多 LoRA 服务可能有明确的公共部分，但成熟框架也可能已经复用基础权重，再做图合并未必产生相同增益。任意两个不同大模型的注意力图、量化尺度和权重布局可能不兼容。即使有相同权重块，也应比较融合、简单权重共享、分时执行与隔离实例，测量准确性、额外算子成本与 cache 行为。

Agent 还会在工具调用时暂停生成，保留会话状态；后续工具返回可能集中触发新的 prefill。它的请求不是独立同分布的短任务。现实系统还要考虑 KV 迁移、TP/PP/EP 通信、前缀缓存命中、租户公平与失败恢复。这些都是 USHER 资源互补思想可以启发的问题，但论文的 2.6 倍或 3.5 倍结果不能直接作为这类部署的容量规划依据。[P §6，第 960 页；现代服务部分为工程延伸]

12. 有推导的练习

练习一：哪个指标能证明不会 OOM？

题目：某 GPU 显示 occupancy 为 80%，dram_utilization 为 9，已分配显存为 12 GB，总容量为 16 GB。能否据此放入“权重大小 3 GB”的模型？

解答：不能直接确定。只有已分配字节数与容量单位相同，但 12 + 3 = 15 GB 也只加了新模型的权重，尚未计入它的激活、KV、workspace、分配器碎片以及运行时峰值。dram_utilization 的 9 是内存活动等级，不是“占了 9 GB”或“还剩 10% 容量”；occupancy 80% 也不证明剩余 20% FLOPS 可以稳定交付。正确下一步是估计和测量峰值容量，再检查带宽、缓存及 SLO，而不是将三个不同口径相加。

练习二：给教学示例二加一个凑批约束

题目：保持每秒 200 个均匀请求、batch 8 执行 10 毫秒、40 毫秒 SLO。忽略其他开销，最早请求最多可以等多久凑批？原来的 8 个请求能否收齐？

解答：凑批等待最多 40 − 10 = 30 毫秒。第八个请求要在 35 毫秒到达，所以不能保证按时收齐八个。实际可在 deadline 到来前发出不满的 batch，或选更小的 batch；但若改为 7 个或更少，执行时间也要重新测量，不能无证据照搬“batch 8 为 10 毫秒”。这说明超时策略与资源估计必须协同，也说明默认只枚举 2 的幂并不涵盖所有在线服务策略。

练习三：消融百分比的分母在哪里？

题目：去掉 OG-Merger 的系统 goodput 假设为 10,000 requests/s，完整系统比它高 55.7%。完整系统是多少？从完整系统删除模块，下降百分比是多少？

解答：完整系统为 10,000 × 1.557 = 15,570 requests/s。删除模块后少 5,570，但这次分母是原来的完整系统 15,570，所以下降 5,570/15,570 ≈ 35.8%。两个百分比描述同一对结果，却因分母不同而不同。若把“高 55.7%”改写成“移除后下降 55.7%”，就夸大了模块贡献。

练习四：预测了每个 kernel，还缺什么？

题目：两个并行分支分别产生 2 GB 和 3 GB 中间结果，随后一个合并算子同时读取两者。若产生两个结果的 kernel 没有同时运行，能否直接断言中间数据峰值最多 3 GB？

解答：不能。即使两个生产 kernel 不重叠，第一个结果仍须存活到合并算子读取它；第二个结果生成后，两者可能同时驻留，至少需要考虑 5 GB，再加合并输出和工作区。kernel 时间重叠与张量生命周期重叠是两个概念。这个练习解释了为什么一个峰值估计器还需要内存存活期验证，也说明我们不能把论文的并发组近似当成通用精确容量分析。

13. 带走什么，不应照搬什么

USHER 最值得学习的，不是某一个阈值，而是一条完整的推理链：批处理改变资源形状；副本改变请求分配与常驻成本；多个模型一起考虑，可能找到单模型优化看不见的互补组合；放置后仍要处理缓存层竞争；最终用满足 SLO 的完成量与成本评价，而不是用“GPU 很忙”自我证明。

也要保留同样清晰的边界。kernel 图预测需要可靠的标签、时序和生命周期；两维预算不等于所有硬件资源均被隔离；权重近似共享需要数值和任务质量检验；大规模模拟不是实机测量；生成式服务需要动态 KV 与阶段化时限。将这两面一起读懂，才算真正理解了 USHER，而不是把它记成“互补模型放在一起，就一定能省三倍 GPU”。
